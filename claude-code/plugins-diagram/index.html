Plugin vs Direct Configuration

Section titled “Plugin vs Direct Configuration”

Plugins package multiple Claude Code components into a single distributable unit. Use plugins when you want to share a coherent set of tools, commands, and conventions across a team or organisation.

CLAUDE_PLUGIN_ROOT vs CLAUDE_PLUGIN_DATA

Section titled “CLAUDE_PLUGIN_ROOT vs CLAUDE_PLUGIN_DATA”

These two environment variables control separate aspects of plugin storage:

VariableControlsDefault locationContains
CLAUDE_PLUGIN_ROOTPlugin installation directory~/.claude/plugins/ (user) or .claude/plugins/ (project)Plugin code: plugin.json, commands, hooks, skills, agents
CLAUDE_PLUGIN_DATAPlugin data and config directory~/.claude/plugin-data/<plugin-name>/User configuration values, plugin state, generated files, local cache

Key distinction: CLAUDE_PLUGIN_ROOT is where Claude Code looks for the plugin’s code. CLAUDE_PLUGIN_DATA is where the plugin writes its runtime state, user config values, and persistent data. Plugins should never write into their own PLUGIN_ROOT — that directory should be treated as read-only after installation.

Plugin Discovery Order and Namespace Resolution

Section titled “Plugin Discovery Order and Namespace Resolution”

When Claude Code starts, it discovers and loads plugins in this order:

Later stages override earlier stages for same-named components. For example, if both the user plugin and project plugin define a /my-plugin:deploy command, the project plugin’s version wins.

Namespace rules:

  • All plugin components are namespaced by plugin name: /plugin-name:command
  • Accessing without namespace (e.g., /deploy) resolves to the closest-scope plugin that provides it
  • Conflicts (two plugins providing /deploy) are reported on startup with claude plugin list --conflicts
  • Skills are auto-invoked without namespace; if two plugins have matching trigger phrases, priority follows discovery order (project > user)
