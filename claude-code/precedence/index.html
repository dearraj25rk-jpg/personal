The Two Distinct Precedence Systems

Section titled “The Two Distinct Precedence Systems”

Claude Code has two fundamentally different precedence systems that work in opposite ways. Confusing them is the most common misconfiguration mistake.

Example 1: Settings conflict (local vs project)

Result:

  • model: claude-opus-4-7 (local wins — it overrides the project key)
  • allow: ["Bash(npm *)", "Bash(npx *)"] (local’s allow list replaces project’s allow list for that key)
  • deny: ["Bash(rm -rf *)"] (project deny still applies — local didn’t specify deny)
  • maxOutputTokens: 8192 (project value — local didn’t set it, so project applies)

Example 2: CLAUDE.md stacking (additive)

Result: Claude sees ALL FIVE instructions concatenated in that order. The Zod requirement is the most specific and appears last — most visible to the model. No conflict occurs — they accumulate. The local DB note is personal and stays out of git.

Example 3: Rules path-scoping (conditional)

Token cost: Reading README.md loads zero rule tokens. Reading src/api/UserCard.tsx loads ~1,200 tokens (both rules). Carefully designed path globs keep costs minimal.

Example 4: Enterprise lock (cannot override)

Result: Enterprise settings are immutable. Despite local settings, Claude still uses sonnet-4-6 and cannot run WebFetch or unrestricted Bash. The enterpriseLock: true flag causes local overrides to be silently ignored for locked keys.
