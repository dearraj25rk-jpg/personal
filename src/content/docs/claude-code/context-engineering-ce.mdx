## Context Engineering — Reference

### What is Context Engineering?

Context engineering (CE) is the practice of deliberately managing what information enters Claude's context window on each API call, and when. Unlike prompt engineering (which focuses on _how_ you phrase instructions), CE focuses on _what_ is present in the context at each turn — and at what cost.

Every token in Claude's context window costs money on every API call. A context window with 800K used tokens costs roughly 4× as much per turn as one with 200K used tokens, even for the same user prompt. CE is the discipline of maximising signal while minimising token cost.

### The Four CE Strategies

| Strategy | Primitive | In Claude Code | When to use |
|----------|-----------|----------------|-------------|
| **WRITE** | Persist to storage | Update CLAUDE.md, write NOTES.md/MEMORY.md | Key decisions, task state, architectural rules |
| **SELECT** | Retrieve selectively | JIT via glob/grep, path-scoped rules, ToolSearch | Any read — avoid bulk-loading |
| **COMPRESS** | Shrink before keeping | `/compact`, `/clear`, summarise bash output, `/effort low` | At 70% usage; between unrelated tasks |
| **ISOLATE** | Separate context windows | Subagents via Task tool, `/branch` worktrees, `/clear` | Research-heavy subtasks, parallel work |

### Context Engineering in Practice — The WRITE→SELECT→COMPRESS→ISOLATE Loop

```
  SESSION START
       │
       ▼
  WRITE: Ensure CLAUDE.md has project context.
  Add architectural decisions to MEMORY.md before starting.
       │
       ▼
  SELECT: Use targeted tools (Grep/Glob/Read) not bulk reads.
  Let path-scoped rules load conditionally.
  Use ToolSearch to defer rarely-needed tool schemas.
       │
       ▼
  Work begins — context fills...
       │
       ▼
  At 60-70% context usage:
  COMPRESS: Run /compact with focus instruction.
  Clear unrelated tool results from context.
       │
       ▼
  Task needs parallel work?
  ISOLATE: Spawn Task (subagent) for independent subtask.
  Use /branch for work requiring a clean context window.
       │
       ▼
  WRITE again: Save outcomes, decisions, state to MEMORY.md.
  SESSION END: /rename for retrieval; /clear for next task.
```

### Token Budget — 1M Window (Sonnet 4.6 / Opus 4.x)

```
1,000,000 tokens total
├── System prompt:                    ~3,100 tokens  (0.3%)
├── Built-in tool schemas:           ~19,800 tokens  (2.0%)
├── ToolSearch deferred savings:     −15,000 tokens  (most tools lazy-loaded v2.1.7+)
├── MCP servers (5 × 2,650):        ~13,250 tokens  (1.3%)
├── Custom agent definitions:         ~2,800 tokens  (0.3%)
├── CLAUDE.md (project root):         ~1,600 tokens  (0.2%)   ← keep under 200 lines
├── Path-scoped rules (matched):        ~500 tokens  (0.1%)   ← conditional load
├── MEMORY.md (auto-memory):         up to 25KB / 200 lines   ← survives compaction
├── Compaction reserve (16.5%):     ~165,000 tokens           ← fires at 835K
└── Available for work:             ~794,000 tokens  (79.4%)
```

**200K window (Haiku 4.5):** Same overheads consume ~9.8% — much tighter than 1M models.

### ToolSearch Lazy Loading (v2.1.7+)

Deferred tools only load their full schema when first used in a session. Built-in tools stay eager (always loaded). This saves **60–80% of tool schema overhead** for most sessions with no configuration required.

| Tool category | Loading | Token cost per tool |
|--------------|---------|---------------------|
| Built-in core (Read, Edit, Bash…) | Eager | ~2,900/tool (always) |
| WebSearch, WebFetch, ToolSearch | Deferred | ~80 name+desc until used |
| MCP tool schemas | Per-connection | ~2,650/server (fixed) |

Check deferred tool state with `/context` — look for the "deferred tools" line.

### MEMORY.md — Durable Auto-Memory

MEMORY.md is Claude Code's durable per-project memory file. Unlike CLAUDE.md, it is:
- Written automatically by Claude during sessions (via `/memory add`)
- Reloaded fully after every compaction (not summarised away)
- Stored at `~/.claude/projects/<hash>/memory/MEMORY.md`
- Limited to 200 lines / 25KB

Use `/memory` to view and edit. Add project-specific facts that should persist across all sessions: database schemas, API quirks, known bugs, architectural decisions already made.

**What belongs in MEMORY.md vs CLAUDE.md:**

| MEMORY.md | CLAUDE.md |
|-----------|----------|
| Discoveries made during sessions | Standing project conventions |
| "We decided to use JWT not sessions" | "Always use JWT for auth" |
| Current task state, blockers | Team conventions and standards |
| Per-session notes | Architectural decisions (permanent) |
| Automatically written by Claude | Manually maintained by team |

### /advisor — CE Superpower

`/advisor` activates dual-model mode: Sonnet 4.6 handles execution (reading files, running tools, writing code) while Opus 4.7 reviews context periodically and provides strategic guidance.

```
Normal session:             Sonnet 4.6 → does everything
/advisor activated:         Sonnet 4.6 → execution
                            Opus 4.7   → strategic advice (periodic)
```

| Mode | Cost per session | Best for |
|------|-----------------|----------|
| Sonnet only | ~$5–15 | Standard feature work |
| /advisor | ~$20–45 | Architecture, ambiguous bugs |
| Opus only | ~$50–150 | Highest complexity, slowest |

Activate: `/advisor` · Force immediate: `/advisor now` · Deactivate: `/advisor off`

### Auto-Compaction Mechanics

Compaction fires at **83.5% context used** (~835K of 1M, ~167K of 200K).  
Each compaction costs **100–200K tokens** to execute. Run `/compact` proactively at 70%.

| Survives compaction | Discarded by compaction |
|--------------------|------------------------|
| Project-root CLAUDE.md (reloaded from disk) | Redundant tool results |
| MEMORY.md (fully reloaded, not summarised) | Path-scoped CLAUDE.md (auto-reloads on next file touch) |
| Architectural decisions (summarised) | Old conversation turns |
| 5 most-recently-accessed files | Raw bash outputs from completed tasks |
| Skills (re-injected up to cap) | Thinking token traces from prior turns |
| NOTES.md / TODO.md if Claude re-reads them | Repeated messages |

### Session Rhythm

```bash
# Session start
/context          # Check starting budget
/effort high      # Default is medium since Mar 2026 — set explicitly
/status           # If parallel sessions — see all running costs

# During work
/compact          # Proactively at ~70% usage
# Ask Claude to write decisions → CLAUDE.md or NOTES.md
/advisor          # For complex architectural decisions
/branch feature-x # Parallel worktree with isolated context window

# Session end
/rename my-task   # Name session for /resume retrieval
# Or: /clear      # Fresh start if switching to unrelated task
```

### CE Anti-Patterns to Avoid

| Anti-pattern | Problem | CE fix |
|-------------|---------|--------|
| Starting every session by asking Claude to "read the entire codebase" | 50-200K tokens wasted on context that won't all be relevant | Use Glob/Grep to SELECT specific files; let rules inject context conditionally |
| Giant CLAUDE.md with 500+ lines | Every session pays full cost; most content irrelevant to current task | Split into path-scoped rules; keep root CLAUDE.md under 200 lines |
| Never running /compact | Context degrades at 85%+; compaction is more expensive than proactive compact | Run /compact at 70% with a focus instruction |
| One giant session for unrelated tasks | Context from task A pollutes task B; costs compound | Use /clear between unrelated tasks; ISOLATE with separate sessions |
| Asking Claude to remember things verbally | Verbal "remember this" has no persistence | WRITE to MEMORY.md or CLAUDE.md explicitly |
| Running 10 MCP servers for every project | 26,500 extra tokens every session | Connect only servers needed for current task via .claude/.mcp.json.local |

## Context Engineering Deep Reference

### Strategy 1: CLAUDE.md Design

CLAUDE.md is the highest-priority persistent context in Claude Code. Because it loads on every session start, every token in it costs money on every API call for the lifetime of the project. Design it for signal density.

**What belongs in CLAUDE.md (high-signal, low-token content):**

- Project purpose (1–3 sentences max)
- Tech stack and language versions (e.g., "Python 3.12, FastAPI 0.111, PostgreSQL 16")
- Repo structure (1 paragraph or short tree — not exhaustive)
- Build and test commands (exact commands, not explanations)
- Team conventions that apply to _every_ file (naming conventions, import order, error handling patterns)
- Pointers to path-scoped rules: "See `rules/typescript.md` for TS-specific conventions"

**What does NOT belong in CLAUDE.md (lazy-load via rules or @import):**

- Framework-specific conventions that only apply to certain files (→ path-scoped rules)
- Long explanations or tutorials (→ linked docs or @import)
- Anything read less than 50% of sessions (→ @import on demand)
- Database schemas or API specs (→ reference files, read selectively)
- CI/CD setup details (→ link to CICD.md)

**Token budget targets by CLAUDE.md scope:**

| Scope | Max lines | Target tokens | Enforcement |
|-------|----------|--------------|-------------|
| Enterprise root (org-wide) | 50 lines | < 3,000 tokens | MDM policy |
| User root (`~/.claude/CLAUDE.md`) | 80 lines | < 5,000 tokens | Self-discipline |
| Project root | 200 lines | < 12,000 tokens | `/context` monitor |
| Subtree (`src/CLAUDE.md`, `tests/CLAUDE.md`) | 100 lines | < 6,000 tokens | Path-scoped auto-load |

Check your CLAUDE.md token cost with `/context` → look at "system" token breakdown.

**@import chain pattern for modular CLAUDE.md:**

```markdown
<!-- Project root CLAUDE.md — keep this under 100 lines -->
# My Project

Stack: TypeScript 5.4, Node 22, PostgreSQL 16, Redis 7

## Build & Test
npm run build   # tsc + bundle
npm test        # vitest
npm run lint    # eslint + prettier

## Key Conventions
- All errors extend AppError (src/errors/base.ts)
- Use Result<T, E> pattern — never throw from services
- See rules/ for language-specific conventions

@import rules/api-standards.md
@import rules/database-conventions.md
```

The `@import` directive is resolved at load time. It adds the target file's content inline but keeps your root CLAUDE.md concise. Each imported file should also be brief — the total loaded token count is the sum of all imports.

### Strategy 2: Rules Scoping

Path-scoped rules load only when Claude opens a matching file. They are the primary tool for keeping per-language or per-directory conventions out of the root CLAUDE.md.

**`paths:` frontmatter for conditional loading:**

```markdown
---
paths:
  - "**/*.ts"
  - "**/*.tsx"
  - "src/types/**"
---
# TypeScript Conventions

- Use `interface` not `type` for object shapes
- Export types separately from implementation files
- All async functions return `Promise<Result<T, AppError>>`
- Use `satisfies` operator for config objects
- Never use `any` — use `unknown` + type guard instead
```

This rule file is **not loaded at startup**. It loads the first time Claude opens a `.ts` or `.tsx` file in the session, and stays loaded for the rest of the session.

**When a rule should be in `rules/` vs `CLAUDE.md`:**

| Belongs in `rules/` | Belongs in `CLAUDE.md` |
|--------------------|----------------------|
| TypeScript-only conventions | Universal naming conventions |
| Test file patterns (`describe`, `it`, `expect`) | Build and test commands |
| SQL query style | Error handling philosophy |
| React component patterns | Folder structure |
| API endpoint conventions | Team communication norms |
| Database migration rules | Project-wide tool preferences |

**Token savings calculation:**

```
Root CLAUDE.md without scoping:
  Loads 500 lines of mixed conventions  →  ~30,000 tokens every session

With path-scoped rules:
  Root CLAUDE.md:   80 lines            →   ~5,000 tokens (always loaded)
  rules/ts.md:      60 lines            →   ~3,600 tokens (TS sessions only)
  rules/tests.md:   40 lines            →   ~2,400 tokens (test files only)
  rules/sql.md:     30 lines            →   ~1,800 tokens (DB sessions only)

  Typical session touches TS + tests:   5,000 + 3,600 + 2,400 = 11,000 tokens
  Savings vs monolithic CLAUDE.md:     ~63% token reduction
  On Sonnet 4.6 at $3/MTok:            ~$0.057 saved per session
  × 100 sessions/month:                ~$5.70/month saved per developer
```

**Example: TypeScript rules only for `*.ts` files**

```markdown
---
paths:
  - "**/*.ts"
  - "!**/*.test.ts"
  - "!node_modules/**"
---
# TypeScript Production Code Rules

Use strict TypeScript: `"strict": true` in tsconfig.json.
Always prefer `interface` over `type` for public API shapes.
Use `readonly` arrays for function inputs: `ReadonlyArray<T>`.
Prefer named exports over default exports (aids tree-shaking).
```

### Strategy 3: Memory Management

Effective session memory management prevents context degradation and controls costs across long sessions.

**Session rhythm — the three phases:**

```
PHASE 1: Session start
  /context        → check starting token budget (should be < 10%)
  /effort high    → set thinking level before complex work
  /memory         → review project memory before starting

PHASE 2: During work (context grows)
  At ~60%:  /compact "Focus on [current task name]"
  Continue working — context now clean + focused
  At ~60% again:  /compact "Focus on [next subtask]"
  Save key decisions: "Update MEMORY.md: we chose JWT over sessions"

PHASE 3: Session end
  /rename my-feature-auth-refactor     → named for /resume retrieval
  /memory                              → verify decisions were saved
  # Or: /clear   if switching to unrelated work
```

**When to use `/compact` vs `/clear`:**

| Situation | Use | Reason |
|-----------|-----|--------|
| Same task, context at 60-70% | `/compact "Focus on X"` | Preserves task context, cheaper than auto-compaction |
| Switching to related sub-task | `/compact "Focus on Y, ignore X details"` | Steers what survives |
| Task complete, new unrelated task | `/clear` | Full clean slate costs less than polluted context |
| Mid-task context hit 83.5% | `/compact` immediately | Prevents expensive auto-compaction |
| Need to preserve all tool results | Neither — use `/branch` | Isolated context window |

**Targeted compaction with steering instruction:**

```bash
# Generic (less effective — model decides what to keep)
/compact

# Steered (much more effective — you tell model what matters)
/compact "Focus on the auth refactor. Keep: JWT structure, middleware changes, test failures. Discard: everything about the payment module."

# Task-switch compaction
/compact "We've finished the database migration. New focus: API rate limiting implementation."
```

**MEMORY.md as compaction-proof storage:**

MEMORY.md is loaded fresh after every compaction. Use it for any fact that must survive `/compact` or `/clear`:

```markdown
<!-- ~/.claude/projects/<hash>/memory/MEMORY.md -->
## Architecture Decisions
- [2026-06-01] Using JWT (not sessions): easier horizontal scaling. Token TTL: 1h access, 7d refresh.
- [2026-06-02] PostgreSQL schema: users table has RLS enabled. See migrations/003_rls.sql.
- [2026-06-03] Rate limiting: 100 req/min per user, Redis sliding window. NOT token bucket.

## Known Issues
- auth middleware currently breaks on OPTIONS preflight (bug #482, fix in progress)
- payment service integration test is flaky — skip with SKIP_PAYMENT_TESTS=1

## Current Work State
- Auth refactor: complete ✓
- Rate limiting: in progress — started RedisRateLimiter class in src/middleware/
- API docs: not started
```

**Naming sessions with `/rename` for retrieval:**

```bash
# Name session before ending (enables /resume later)
/rename auth-refactor-jwt-middleware-2026-06-03

# List named sessions
/sessions

# Resume a named session
/resume auth-refactor-jwt-middleware-2026-06-03
```

### Strategy 4: Compaction Control

**Auto-compaction threshold and timing:**

Auto-compaction fires at **83.5% context used** by default (v2.1.89+). At 1M token window, that's ~835K tokens. At 200K (Haiku), that's ~167K tokens.

The compaction process itself consumes **100–200K tokens** to summarise the context. Running it proactively at 70% (before the auto-threshold) saves this overhead and gives you control over the summary focus.

```
Context usage over a long session:

0%  ──────────────────────────────────── 100%
│                                            │
│    WORK           │compact│  WORK          │
│    ──────────────►│       │──────────────► │
│                   70%     │               83.5%
│                   ^        │               ^
│                   Optimal  │               Auto-fires here
│                   compact  │               (costs more, less focused)
│                   zone     │
```

**Circuit breaker (v2.1.89+):**

If compaction fails (e.g., model unavailable, network timeout), the circuit breaker prevents the session from entering an infinite retry loop. The session pauses and reports the error rather than consuming tokens in failed compaction attempts.

**Compaction survival matrix — what stays, what goes:**

| Content | Survives `/compact`? | Why |
|---------|---------------------|-----|
| Project-root `CLAUDE.md` | Yes — full text reloaded from disk | Disk-persisted, not summarised |
| `MEMORY.md` | Yes — full text reloaded | Disk-persisted, not summarised |
| Path-scoped rules (matched) | Yes — reloaded on next file touch | Disk-persisted |
| Architectural decisions (in conversation) | Partially — summarised | In summary |
| 5 most-recently-accessed files | Yes — retained verbatim | Recent = relevant |
| Skills (injected at session start) | Yes — re-injected up to cap | Session-level persistence |
| `NOTES.md` / `TODO.md` (if re-read) | Yes — if Claude re-reads after compact | Must be re-read |
| Raw bash output from completed tasks | Discarded | Not summarised |
| Thinking token traces from prior turns | Discarded | Too expensive to retain |
| Old conversation turns | Summarised or discarded | Core compaction target |
| Redundant tool results | Discarded | No longer needed |

**Proactive compaction at 70% (saves $0.10–0.50 per session):**

```bash
# Check current usage
/context
# Output shows: "Context: 142,341 / 200,000 tokens (71.2%)"

# Compact now (proactive at 71%) with focus steering
/compact "Summarise: we refactored auth to JWT. Keep: the new middleware structure, failing test names, next steps. Discard: old session/cookie implementation details."

# Verify compact succeeded
/context
# Output shows: "Context: 38,200 / 200,000 tokens (19.1%)"
```

### Session Rhythm Patterns by Work Type

**Pattern 1: Quick task (under 30 minutes)**

```bash
/clear                          # Clean context for unrelated work
# No compact needed — session ends before context fills
# Just /clear between tasks in the same Claude session
```

**Pattern 2: Half-day feature (2–4 hours)**

```bash
/context                        # Check starting budget
/effort high                    # Ensure full thinking for complex work

# ... work for 1–2 hours ...

/compact "Focus on [feature-name] implementation. Keep: current file changes, test failures. Discard: early exploration."
# Continue work

/rename feature-name-2026-06-03  # Name for retrieval if interrupted
```

**Pattern 3: All-day architecture session (6–8 hours)**

```bash
/context && /effort high         # Start clean

# ... 2 hours of work ...
/compact "Architecture decision: chose event-sourcing. Keep: event schema, aggregate pattern. Discard: initial CRUD exploration."

# Save decisions immediately after compact
# "Please update MEMORY.md: we chose event-sourcing for the order domain because [reasons]"

# ... 2 more hours ...
/compact "Keep: current implementation of OrderAggregate. Discard: earlier OrderService attempt."

# ... end of day ...
/rename architecture-event-sourcing-2026-06-03
# "Please update MEMORY.md with today's decisions before I close the session"
```

**Pattern 4: Multi-day project**

```bash
# Day 1 end ritual:
# "Summarise today's key decisions and save them to MEMORY.md"
/rename project-auth-day1

# Day 2 start:
/resume project-auth-day1       # Optionally resume; or /clear for fresh start
/memory                         # Review decisions saved yesterday
/context                        # Check budget
# "Read MEMORY.md and CLAUDE.md, then summarise where we left off"

# Repeat daily — MEMORY.md is the cross-session state store
```
