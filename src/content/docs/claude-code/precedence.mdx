### The Two Distinct Precedence Systems

Claude Code has **two fundamentally different** precedence systems that work in opposite ways. Confusing them is the most common misconfiguration mistake.

```
╔══════════════════════════════════════════════════════════════╗
║  SYSTEM 1: SETTINGS FILES (permissions, model, options)      ║
║                                                              ║
║  Enterprise > CLI flags > local > project > user             ║
║                                                              ║
║  Rule: Higher layer WINS — lower layer key is DISCARDED      ║
║                                                              ║
║  Example: if enterprise sets model=opus-4-7                  ║
║           and project sets model=sonnet-4-6                  ║
║           → opus-4-7 is used. Project setting ignored.       ║
╠══════════════════════════════════════════════════════════════╣
║  SYSTEM 2: CONTEXT FILES (CLAUDE.md, Rules, Memory)          ║
║                                                              ║
║  Enterprise → user → project → subdirs → local → rules      ║
║                                                              ║
║  Rule: ALL layers LOAD and APPEND (concatenation)            ║
║        Later-loaded files appear AFTER earlier in context    ║
║        More specific = later = more visible to model         ║
║                                                              ║
║  Example: if user CLAUDE.md says "use TypeScript strict"     ║
║           and project CLAUDE.md says "use Express for APIs"  ║
║           → Claude sees BOTH instructions simultaneously     ║
╚══════════════════════════════════════════════════════════════╝
```

### Conflict Resolution Rules

| Conflict type | Resolution | Why |
|--------------|-----------|-----|
| Enterprise vs user setting | Enterprise always wins | Managed policy cannot be bypassed |
| Enterprise vs CLI flag | Enterprise always wins | CLI flags cannot override MDM |
| Enterprise vs project setting | Enterprise always wins | Same reason |
| CLI flag vs local settings | CLI flag wins | Flags are per-invocation override |
| Local settings vs project settings | Local settings win | `.local.json` is highest non-enterprise |
| Project settings vs user settings | Project settings win | Closer scope wins |
| User settings (key not set in project) | User setting applies | Inheritance fills gaps |
| Multiple CLAUDE.md (different paths) | All load; deeper path appended last | Additive, not replacing |
| Two CLAUDE.md at same level | Not possible — one file per directory | N/A |
| Same key in two rules files | Last-loaded alphabetically wins | Files sorted before loading |
| Rules `paths:` overlap | Both rules load for overlapping files | Additive |
| Skills loaded simultaneously | Each skill is isolated, no conflict | Separate injection points |
| CLAUDE.md vs CLAUDE.local.md | Both load; .local.md appended after | Additive — .local adds, not replaces |
| @import in CLAUDE.md | Imported file content inlined at that point | Single unified document |

### What Happens When Files Conflict — Concrete Examples

**Example 1: Settings conflict (local vs project)**

```json
// .claude/settings.json (project — committed to git)
{
  "permissions": {
    "allow": ["Bash(npm *)", "Read", "Edit"],
    "deny": ["Bash(rm -rf *)"]
  },
  "model": "claude-sonnet-4-6",
  "maxOutputTokens": 8192
}

// .claude/settings.local.json (local — gitignored)
{
  "model": "claude-opus-4-7",
  "permissions": {
    "allow": ["Bash(npm *)", "Bash(npx *)"]
  }
}
```

**Result:**
- `model`: `claude-opus-4-7` (local wins — it overrides the project key)
- `allow`: `["Bash(npm *)", "Bash(npx *)"]` (local's allow list replaces project's allow list for that key)
- `deny`: `["Bash(rm -rf *)"]` (project deny still applies — local didn't specify deny)
- `maxOutputTokens`: `8192` (project value — local didn't set it, so project applies)

**Example 2: CLAUDE.md stacking (additive)**

```
~/.claude/CLAUDE.md:
  "Always use TypeScript strict mode. Prefer functional patterns."

CLAUDE.md (project root):
  "This is a Node.js 20 Express REST API.
   Use Prisma for database access. Return RFC 7807 errors."

src/CLAUDE.md:
  "All source files use ESM import syntax. No require()."

src/api/CLAUDE.md:
  "All API routes must validate input with Zod before processing."

CLAUDE.local.md (root):
  "My local DB is at localhost:5433, not the default 5432."
```

**Result:** Claude sees ALL FIVE instructions concatenated in that order. The Zod requirement is the most specific and appears last — most visible to the model. No conflict occurs — they accumulate. The local DB note is personal and stays out of git.

**Example 3: Rules path-scoping (conditional)**

```yaml
# .claude/rules/frontend.md — paths: [src/**/*.tsx, src/**/*.css]
# .claude/rules/backend.md  — paths: [src/api/**, tests/api/**]
# .claude/rules/database.md — paths: [src/db/**, migrations/**]
```

```
File Claude reads:           Rules that load:
─────────────────────────────────────────────────────
src/components/Button.tsx    frontend.md only
src/api/routes.ts            backend.md only
src/api/UserCard.tsx         backend.md + frontend.md
migrations/001_init.sql      database.md only
tests/api/auth.test.ts       backend.md only
README.md                    (none — no rule matches)
```

Token cost: Reading `README.md` loads zero rule tokens. Reading `src/api/UserCard.tsx` loads ~1,200 tokens (both rules). Carefully designed path globs keep costs minimal.

**Example 4: Enterprise lock (cannot override)**

```json
// ~/.claude/managed-settings.json (enterprise-managed)
{
  "allowedTools": ["Read", "Edit", "Bash(git *)"],
  "model": "claude-sonnet-4-6",
  "enterpriseLock": true
}
```

```json
// .claude/settings.local.json (developer's local file)
{
  "allowedTools": ["Read", "Edit", "Bash", "WebFetch"],
  "model": "claude-opus-4-7"
}
```

**Result:** Enterprise settings are immutable. Despite local settings, Claude still uses `sonnet-4-6` and cannot run `WebFetch` or unrestricted `Bash`. The `enterpriseLock: true` flag causes local overrides to be silently ignored for locked keys.

### Override Syntax Examples

```json
// .claude/settings.json — permission examples
{
  "permissions": {
    "allow": [
      "Bash(git *)",              // Any git subcommand
      "Bash(npm run *)",          // npm run scripts only (not npm install)
      "Bash(npm install)",        // Exact command — no args variation
      "Read",                     // All file reads
      "Edit",                     // All file edits
      "Bash(docker ps)",          // Exact docker command
      "Bash(pytest src/**)",      // Glob in command args
      "Bash(curl -s https://api.example.com/*)"  // URL pattern
    ],
    "deny": [
      "Bash(rm -rf *)",           // Protect against recursive deletes
      "Bash(git push --force*)",  // Block force pushes
      "Bash(sudo *)",             // No privilege escalation
      "WebFetch(http://*)",       // HTTPS only (deny plain HTTP)
      "Bash(dd if=*)",            // Block disk operations
      "Bash(mkfs.*)",             // Block filesystem formatting
      "Bash(curl * | bash)"       // Block curl-pipe-to-shell
    ]
  }
}
```

### Common Mistakes Table

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Committing `.claude/settings.local.json` | Personal API keys or model choices shared with team | Add to `.gitignore`: `.claude/settings.local.json` |
| Putting everything in root CLAUDE.md | Huge CLAUDE.md (500+ lines); expensive every session | Split into `.claude/rules/*.md` with `paths:` — zero cost until needed |
| Using `CLAUDE.local.md` thinking it overrides | Both files apply; "override" instructions are additive | Understand `.local.md` appends. Use settings files for actual overrides. |
| Expecting subdirectory CLAUDE.md to isolate | All parent CLAUDE.md files still load | Use subagents with `allowedPaths` for true isolation |
| Setting `model` in project expecting precedence over enterprise | Enterprise always wins — project setting silently ignored | Check: `cat ~/.claude/managed-settings.json` |
| Relying on rule file load order by filename | Natural sort: alphabetical, only matters for same-key conflicts | Name files with numeric prefix: `01-core.md`, `02-api.md` |
| Expecting `/compact` to reload settings | Settings are NOT reloaded after compaction — only CLAUDE.md and MEMORY.md reload | Restart session to pick up settings changes |
| Using `deny` expecting it to supersede `allow` | Deny wins for the same pattern; broader `allow` can supersede narrower `deny` | Be explicit: deny broad, allow narrow |
| @import in CLAUDE.local.md | Imported path must be accessible on each developer's machine | Works correctly but requires local path to exist |
| Setting `maxTurns` thinking it controls cost | `maxTurns` limits iterations, not tokens or cost per turn | Use `--max-budget-usd` for hard cost ceiling |

### Precedence Quick-Check Flowchart

```
Is the key in enterprise managed-settings.json?
  YES → Enterprise value is FINAL. Stop.
  NO  ↓

Is the key in CLI flags for this invocation?
  YES → CLI value applies (for this run only). Stop.
  NO  ↓

Is the key in .claude/settings.local.json?
  YES → Local value applies. Stop.
  NO  ↓

Is the key in .claude/settings.json?
  YES → Project value applies. Stop.
  NO  ↓

Is the key in ~/.claude/settings.json?
  YES → User value applies. Stop.
  NO  ↓

Default value from Claude Code applies.
```

### Key Architecture Insight

The most important thing to understand about Claude Code precedence is that **settings files and context files work in opposite directions**:

- **Settings files (JSON):** Higher layer WINS. Use for anything that can conflict: model choice, permissions, token limits.
- **Context files (CLAUDE.md, rules):** ALL layers load additively. Use for anything where more context is better: coding standards, architecture decisions, domain knowledge.

This explains why you can have a 10-file hierarchy of CLAUDE.md files without any conflicts — they all stack — while having a single `model` key that can only come from one source.

→ Full reference: [Configuration Guide — CLAUDE.md vs Skills vs Rules](./claude-code-config-guide)

## Settings Keys — What Enterprise Can Lock

Enterprise managed settings can lock any key in `settings.json`. Here are the most commonly locked keys and their semantics:

| Key | What it controls | Enterprise can lock? | User can override if unlocked? |
|-----|-----------------|---------------------|-------------------------------|
| `model` | Default model for sessions | Yes | Yes — via `/model` or `--model` |
| `maxCostPerSession` | Maximum spend per session | Yes | Yes — user can set lower, not higher |
| `permissions.allow` | Tool allowlist | Yes (adds restrictions) | Yes (can add more) |
| `permissions.deny` | Tool blocklist | Yes (adds restrictions) | Yes (can add more) |
| `env.DISABLE_UPDATES` | Prevent auto-updates | Yes | Yes — set in any settings file |
| `env.DISABLE_TELEMETRY` | Opt out of telemetry | Yes | Yes — but enterprise may force enable |
| `hooks` | Automation hooks | Yes (enterprise hooks fire alongside) | Yes (project/user hooks still fire) |
| `defaultStyle` | Default output style | Yes | Yes — can override via `/config` |
| `mcp.mcpServers` | MCP server definitions | Yes — adds servers, cannot remove enterprise servers | Yes — can add, cannot remove enterprise |

**Enterprise lock semantics:** Enterprise settings don't just set defaults — they lock. A key set in `managed-settings.json` cannot be overridden by ANY other settings file, CLI flag, or environment variable. The only exception is CLAUDE.md context injection, which is additive (enterprise CLAUDE.md is always loaded, but project CLAUDE.md is also loaded after it).

## Managed Settings vs CLAUDE.md — Different Systems

These two enterprise features control entirely different aspects of Claude Code behavior and do NOT interact:

| Feature | Controls | Format | Override level |
|---------|----------|--------|----------------|
| Managed Settings (`managed-settings.json`) | **Permissions, tools, model, costs, hooks** — everything in settings.json | JSON | Cannot be overridden by any non-enterprise mechanism |
| Enterprise CLAUDE.md | **Instructions, context, coding standards, policies in natural language** | Markdown | Always loaded; project CLAUDE.md adds to it, doesn't replace it |

**Example:** You can use managed settings to restrict Claude to only specific tools (`permissions.deny: ["Bash"]`) AND use enterprise CLAUDE.md to tell Claude your team's coding standards. These work independently and both apply simultaneously.

**Why this matters:** Some teams try to use CLAUDE.md to restrict tool access. This does NOT work — CLAUDE.md is natural language instructions, not a security control. Tool restrictions MUST be in `permissions.deny` inside managed settings. Claude might follow CLAUDE.md instructions to not use Bash, but a prompt injection or jailbreak attempt could override natural-language restrictions. Managed settings permissions are enforced at the binary level, not the LLM level.
