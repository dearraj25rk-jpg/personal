## Session Lifecycle — Quick Reference

### Phase 1: Initialization — Detailed Load Order with Timing

The initialization phase loads all configuration and context files before the first prompt is processed. Files load in strict priority order — later files can override earlier ones unless enterprise lock prevents it.

```
TIME 0ms — Process start
  │
  ├─ [~5ms]   Enterprise managed settings loaded (MDM/managed path)
  │              └─ ~/.claude/managed-settings.json  ← LOCKED, no override possible
  │              └─ Windows: HKCU\SOFTWARE\Anthropic\Claude   (Windows Registry)
  │              └─ macOS:   /Library/Managed Preferences/com.anthropic.claude.plist
  │
  ├─ [~8ms]   User settings loaded
  │              └─ ~/.claude/settings.json
  │              └─ Merged ON TOP of managed — managed keys are immutable
  │
  ├─ [~10ms]  Project settings loaded
  │              └─ .claude/settings.json            ← commit to git
  │              └─ Overrides user settings for same keys (closer scope wins)
  │
  ├─ [~11ms]  Local settings loaded
  │              └─ .claude/settings.local.json      ← gitignore this!
  │              └─ Highest precedence non-enterprise settings
  │
  ├─ [~12ms]  Keybindings loaded
  │              └─ ~/.claude/keybindings.json
  │              └─ Chord and modifier key bindings applied
  │
  ├─ [~15ms]  Enterprise CLAUDE.md loaded (if managed path set)
  │              └─ Injected as first block in system prompt
  │
  ├─ [~18ms]  User CLAUDE.md loaded
  │              └─ ~/.claude/CLAUDE.md              ← cross-project context
  │              └─ Appended AFTER enterprise CLAUDE.md
  │
  ├─ [~20ms]  Project CLAUDE.md loaded
  │              └─ CLAUDE.md (repo root)            ← main project context
  │              └─ Appended AFTER user CLAUDE.md
  │              └─ @import directives resolved recursively here
  │
  ├─ [~22ms]  Sub-directory CLAUDE.md files loaded
  │              └─ Any CLAUDE.md in parent dirs of CWD (cumulative, depth-first)
  │              └─ e.g. src/CLAUDE.md → src/api/CLAUDE.md (most specific last)
  │
  ├─ [~23ms]  CLAUDE.local.md loaded
  │              └─ CLAUDE.local.md (repo root)      ← personal overrides
  │              └─ Appended last in CLAUDE.md chain
  │
  ├─ [~25ms]  Path-scoped Rules indexed (NOT yet loaded into context)
  │              └─ .claude/rules/*.md               ← deferred until file path matches
  │              └─ File names sorted alphabetically before indexing
  │              └─ paths: frontmatter field compiled to glob matchers
  │
  ├─ [~30ms]  Auto-Memory loaded
  │              └─ ~/.claude/projects/<hash>/memory/MEMORY.md
  │              └─ Hash = SHA256 of absolute project path
  │              └─ Up to 200 lines / 25KB — truncated from bottom if over limit
  │
  ├─ [~35ms]  MCP server connections established
  │              └─ .mcp.json → spawn stdio servers or connect HTTP servers
  │              └─ Tool schemas from each server fetched and registered
  │              └─ ~2,650 tokens consumed per connected server
  │
  ├─ [~50ms]  Hooks registered from settings.json
  │              └─ PreToolUse, PostToolUse, PreBash etc. registered
  │              └─ http handlers validated (URLs reachable?)
  │
  └─ [~55ms]  First prompt accepted — session ready
                 └─ /context now shows live token budget breakdown
```

### Token Load Order Diagram

Understanding which files consume context window budget on startup is critical for designing efficient projects. Everything "at init" is a fixed cost before you type a single word.

```
Context window at session start (1,000,000 tokens, Sonnet 4.6)
═══════════════════════════════════════════════════════════════
 Category                            Tokens        % of 1M
───────────────────────────────────────────────────────────────
[███] System prompt                  ~3,100         0.31%
[███████████████] Built-in tool schemas
     (eager core: Read, Edit, Bash,
      Write, Grep, Glob, Task…)      ~4,800         0.48%
[█] Deferred tool stubs              ~80/tool       varies
    (names only until first use)
[██████████] MCP tool schemas        ~2,650/server  varies
[███] Enterprise CLAUDE.md           variable        —
[███] User CLAUDE.md                 variable       aim <2,000
[████████] Project CLAUDE.md         variable       aim <4,000
[████████] CLAUDE.local.md           variable        —
[███] Auto-Memory MEMORY.md          up to 25KB      —
───────────────────────────────────────────────────────────────
[···] Rules files                    0 at start     (deferred)
[···] Skills                         0 at start     (deferred)
[···] Commands                       0 at start     (deferred)
[···] Agents                         0 at start     (deferred)
───────────────────────────────────────────────────────────────
Compaction reserve (fires at 83.5%) ~165,000        16.5%
Available for actual work           ~794,000        79.4%
═══════════════════════════════════════════════════════════════
```

**Key insight:** Rules files do NOT consume context on startup — they load conditionally when Claude touches files matching their `paths:` globs. This is the primary reason to prefer rules over CLAUDE.md for domain-specific instructions. A project with 20 well-scoped rules files uses 0 tokens for 19 of them on any given file access.

**Haiku 4.5 caveat:** With a 200K context window, the same overheads consume ~9.8% — significantly tighter. Keep CLAUDE.md under 100 lines when using Haiku.

### Phase 2: Tool Loop — Detailed Flow

```
Your prompt arrives
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│  PrePrompt hook fires (blockable)                         │
│  → Can modify or reject the prompt before it goes to API │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│  Claude API call                                          │
│    • System prompt (built-in + all loaded CLAUDE.md)     │
│    • Conversation history                                 │
│    • Tool schemas (eager + any deferred already resolved) │
│    • Your message                                         │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
             stop_reason == "tool_use"?
                  │              │
                 YES             NO
                  │              │
                  ▼              ▼
         Execute tool       PostPrompt hook
              │             → End of turn
              │
              ├─ PreToolUse hook fires (blockable, exit 2 = user sees error)
              │    └─ e.g. block rm -rf, log all writes, require approval
              │
              ├─ Tool runs
              │    ├─ Read / Glob / Grep — file system access
              │    ├─ Edit / Write / MultiEdit — file mutations
              │    ├─ Bash — shell execution
              │    ├─ WebFetch / WebSearch — network access
              │    ├─ Task — spawn subagent
              │    ├─ ToolSearch — resolve deferred tool schema
              │    └─ MCP tools — delegated to MCP server
              │
              ├─ PostToolUse hook fires (observe-only)
              │    └─ e.g. log tool result, trigger CI, send Slack alert
              │
              ├─ Check: does touched file path match any rules/ glob?
              │    └─ YES → inject matching rule into context window now
              │    └─ Each matched rule: ~300–800 tokens, loaded once per session
              │
              └─ Append tool result → loop back to API call
```

### Phase 3: Compaction — Mechanics Deep Dive

Compaction is the mechanism Claude Code uses to continue working when the context window approaches its limit. Understanding it prevents surprise costs and context loss.

```
Context usage meter
═══════════════════════════════════════════════════════════════
0%                    60%    70%    83.5%              100%
│                      │      │      │                    │
│  ← normal work →     │      │      │                    │
│                      │      │      │                    │
│                      │  ← RUN /compact HERE (cheapest)  │
│                      │      │      │                    │
│                       ← manual /compact still good      │
│                              │      │                    │
│                              │ ← AUTO fires at 83.5%    │
│                              │      │                    │
│                              │  100K–200K tokens spent  │
│                              │  summarising history      │
│                                     │ DANGER ZONE:       │
│                                     │ Re-trigger risk    │
═══════════════════════════════════════════════════════════════
```

**What compaction does, step by step:**
1. Pauses the tool loop
2. Sends the entire conversation history to Claude in a separate call
3. Claude produces a dense summary (~1,000–3,000 tokens) of what happened
4. Summary replaces the conversation history in the context window
5. CLAUDE.md reloads from disk (fresh copy, not summarised)
6. MEMORY.md reloads fully from disk (not summarised)
7. Path-scoped rules re-index (reloaded on next file match)
8. Active skills re-inject up to the skill cap
9. Tool loop resumes with the new compressed context

**Compaction survival matrix:**

| Item | Survives compaction? | Notes |
|------|---------------------|-------|
| Project CLAUDE.md | Yes — reloaded from disk | Keep it authoritative |
| User CLAUDE.md | Yes — reloaded from disk | — |
| MEMORY.md | Yes — fully reloaded | Best place for durable facts |
| Architectural decisions (in MEMORY.md) | Yes | Write them explicitly |
| /todos list | Yes — re-read by Claude | Claude re-reads TODO.md |
| Conversation history | No — summarised | Only gist survives |
| Raw bash output | No | Gone after compaction |
| Path-scoped rules | Re-indexed | Load on next file match |
| Deferred tool schemas | Re-resolved | Load on next use |
| Thinking token traces | No | Gone entirely |
| Open file contents in context | No | Re-read if needed |

- Triggers at **~83.5% context used** (auto) or via `/compact [instructions]`
- Compaction itself costs **100–200K tokens** to execute (Sonnet 4.6 prices)
- Circuit breaker (v2.1.89+) prevents re-triggering within 2 minutes
- **Best practice:** Run `/compact` proactively at 70% to avoid the costlier auto-compaction
- Pass instructions: `/compact Focus on the auth module changes` to guide summary

### Phase 4: Shutdown

```
User closes session / Ctrl+C / natural completion
    │
    ├─ Stop hook fires (blockable — exit 2 to prevent shutdown with message)
    │    └─ Use to: save state, run cleanup scripts, post to Slack
    │
    ├─ Cleanup
    │    ├─ Temp files removed
    │    ├─ MCP servers disconnected (SIGTERM, then SIGKILL after 5s)
    │    └─ Background monitors stopped
    │
    ├─ PostSessionEnd hook fires (observe-only — async, Claude is gone)
    │    └─ Use for: audit logging, cost reporting, metric collection
    │
    ├─ Session state serialised to disk for /resume
    │    └─ ~/.claude/projects/<hash>/sessions/<session-id>.json
    │
    └─ Session available: /resume <session-id-or-name>
         └─ /rename <name> before closing to make retrieval easier
```

### Key Architecture Principles

1. **Additive not overriding (CLAUDE.md):** Multiple CLAUDE.md files all load — they stack, not replace. The enterprise file loads first, user next, project next, subdirectory last. Think of it as concatenation in order of specificity.

2. **Overriding (settings):** Settings files do override — local beats project beats user beats managed (except enterprise managed always wins for any key it sets). This is the opposite of CLAUDE.md behavior.

3. **Zero-cost deferral:** Rules, skills, agents, commands, and output styles cost 0 tokens until triggered. Design your project to exploit this — move all domain-specific guidance into `.claude/rules/*.md` with appropriate `paths:` globs.

4. **Compaction survivors:** MEMORY.md and CLAUDE.md survive compaction by reloading from disk. Use them for anything that must persist long sessions. Never rely on the conversation history alone for critical facts.

5. **Hash-based project identity:** The project identity key (used for MEMORY.md path and session storage) is the SHA256 of the absolute path to the project root. Moving a project to a different path creates a new identity — run `/memory migrate` after relocating.

6. **MCP token cost is per-server, not per-tool:** Each connected MCP server costs ~2,650 tokens regardless of how many tools it exposes. Connect only the servers you actually use in a session; use `.claude/.mcp.json.local` for server subsets.

### Session Cost Estimation

```
Rough formula for a Sonnet 4.6 session:

Base overhead (init) = 8,000 tokens
  + CLAUDE.md total length (tokens)
  + MCP servers × 2,650
  + MEMORY.md length

Per-turn cost ≈ prompt_tokens + (avg_tool_calls × 1,500) + output_tokens

Total ≈ base + (turns × per_turn_cost)

  Base:       8,000
```

## Session Lifecycle — Phase-by-Phase Breakdown

This section provides a comprehensive written explanation of every phase in a Claude Code session, expanding on the diagrams above with deeper behavioral details, edge cases, and design rationale.

### Init Phase — What Really Happens

The init phase is deterministic and synchronous. Claude Code resolves a single merged configuration state before accepting any user input. The sequence cannot be reordered and each step is idempotent on restart.

**Step 1 — Enterprise policy enforcement (t=0–5ms)**

The very first action is checking for managed policy. On macOS, this is a plist under `/Library/Managed Preferences/`. On Windows, it is a registry hive under `HKCU\SOFTWARE\Anthropic\Claude`. On Linux, it is `~/.claude/managed-settings.json` deployed by MDM tooling (e.g. Jamf, Kandji, Intune).

Policy keys are loaded into an immutable locked map. Every subsequent configuration merge step checks this map — any key present in the locked map is skipped during merge. This means the enterprise administrator's value is final regardless of what other files say.

**Step 2 — Settings merge cascade (t=5–12ms)**

Settings files are merged in precedence order from lowest to highest: user → project → local. The merge algorithm is a deep merge with last-writer-wins semantics for scalar values and array replacement (not append) for list values like `permissions.allow`. This is why local settings' `allow` list completely replaces the project `allow` list rather than extending it.

**Step 3 — Context file assembly (t=15–23ms)**

CLAUDE.md files are concatenated, not merged. Each file is appended as a separate block with a delimiter comment so the model can distinguish sources. The order is enterprise → user → project root → subdirectories (depth-first, shallowest parent first) → CLAUDE.local.md.

`@import` directives in any CLAUDE.md file are resolved inline at parse time. An `@import ./docs/standards.md` in the project CLAUDE.md inlines that file's content at that exact position in the concatenated document. Circular imports are detected and skipped with a warning.

**Step 4 — Rules indexing (t=25ms)**

Rules files are NOT loaded into context. Only their frontmatter is parsed to extract `paths:` glob patterns. These patterns are compiled into a glob matcher and stored in an in-memory index keyed by rule file path. The actual rule content remains on disk until a path match triggers loading.

**Step 5 — MEMORY.md load (t=30ms)**

The project identity hash is computed as SHA256 of the absolute project root path. Claude Code looks up `~/.claude/projects/<hash>/memory/MEMORY.md` and loads its content into the system prompt after all CLAUDE.md files. If the file does not exist, this step is a no-op. If it exceeds 200 lines or 25KB, it is truncated from the bottom (oldest entries removed first).

**Step 6 — MCP server bootstrap (t=35ms)**

MCP configuration files are read in merge order: user `.mcp.json` → project `.mcp.json` → local `.claude/.mcp.json.local`. For each configured server, Claude Code either spawns a stdio subprocess or opens an HTTP/SSE connection. Tool schema fetching happens synchronously — if a server fails to respond, its tools are unavailable but the session still starts. Each successfully connected server adds ~2,650 tokens to the fixed context overhead.

**Step 7 — Hook registration (t=50ms)**

All `hooks` entries from the merged settings are registered. For `http` handler types, the URL is validated for reachability (a HEAD request is issued). For `command` handlers, the executable is checked for existence and execute permission. Invalid handlers are logged as warnings, not errors — the session starts regardless.

## Hook Injection Points

Hooks fire at precise, named points in the lifecycle. Understanding where each event fires lets you build automation that intervenes at exactly the right moment.

```
SESSION LIFECYCLE WITH ALL HOOK INJECTION POINTS
══════════════════════════════════════════════════════════════════

  [PreSessionStart] ← fires before any init; can abort session
         │
    INIT PHASE (t=0–55ms)
         │
  [PostSessionStart] ← session is ready; cannot abort
         │
    ┌────▼──────────────────────────────────────────────┐
    │  TOOL LOOP                                         │
    │                                                    │
    │  [PrePrompt]    ← fires before each API call      │
    │       │                                            │
    │  Claude thinks / generates tool calls              │
    │       │                                            │
    │  [PostPrompt]   ← fires after each API response   │
    │       │                                            │
    │  For each tool call:                               │
    │    [PreToolUse]    ← fires before any tool        │
    │    [PreBash]       ← fires before Bash only       │
    │    [PreFileWrite]  ← fires before Write/Edit      │
    │    [PreFileRead]   ← fires before Read            │
    │    [PreWebFetch]   ← fires before WebFetch        │
    │    [PreWebSearch]  ← fires before WebSearch       │
    │    [PreTask]       ← fires before Task (subagent) │
    │    [PreMCPTool]    ← fires before any MCP tool    │
    │         │                                          │
    │    TOOL EXECUTES                                   │
    │         │                                          │

    │    [PostMCPTool]         ← MCP tool completed     │

    │         │                                          │
    │    Loop back to PrePrompt                          │
    │                                                    │
    │  When context hits 83.5%:                          │
    │    [PreCompact]   ← can delay or abort compaction │
    │         │                                          │

    │    [PostCompact]  ← compaction done; context fresh│
    │                                                    │
    └──────────────────────────────────────────────────┘
         │
  [Stop]           ← user closes / Ctrl+C; can block
         │
    CLEANUP
         │
  [PostSessionEnd]  ← async; session is fully gone

══════════════════════════════════════════════════════════════════
```

**Blockable events** (exit 2 = user sees message, exit 3 = Claude sees message):
`PreSessionStart`, `Stop`, `PreToolUse`, `PreBash`, `PreFileWrite`, `PreWebFetch`, `PreWebSearch`, `PreTask`, `PreMCPTool`, `PrePrompt`, `PreCompact`, `PreAgentTeamMessage`

**Observe-only events** (exit code ignored, cannot block):
All `Post*` events — used for logging, alerting, and side-effect triggering only.

## Context Budget Allocation

Understanding how the 1,000,000-token context window is actually allocated across a typical session helps you make informed trade-offs in project design.
