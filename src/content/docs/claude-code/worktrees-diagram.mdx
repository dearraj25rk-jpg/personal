## Worktrees Quick Reference

### What is a Git Worktree?

A Git worktree is a separate checkout of a repository that **shares the same `.git/` database** as your main working copy. Unlike cloning, worktrees:
- Share all commit history, objects, branches, and remotes
- Each worktree has exactly one branch checked out
- Are lightweight — no duplication of the `.git/` directory
- Can be created and deleted in seconds

```bash
# Create a worktree for a new feature branch
git worktree add ../my-project-feature-auth feature/auth

# Or use Claude Code's built-in command
> /branch feature/auth
# → creates worktree at ../my-project-feature-auth
# → opens new terminal window focused on that directory
# → starts a fresh Claude Code session in the new branch context
```

### The /branch Command

| Step | What happens |
|------|-------------|
| `/branch <name>` | Claude creates the git worktree at the sibling path |
| Git checkout | Branch `<name>` is created and checked out in the new worktree |
| New terminal | A new terminal window/pane opens with CWD set to the worktree |
| Fresh context | A new Claude Code session initialises — clean context, loads CLAUDE.md for that branch |
| Independence | The new session has zero knowledge of your current session |

### Parallel Session Layout

```
~/projects/my-project/              ← main worktree (branch: main)
  └── Claude Code session 1: "Fix billing bug"

~/projects/my-project-feature-auth/ ← worktree 1 (branch: feature/auth)
  └── Claude Code session 2: "Implement OAuth flow"

~/projects/my-project-feature-ui/   ← worktree 2 (branch: feature/ui)
  └── Claude Code session 3: "Build settings page"
```

Each session:
- Has its own context window and conversation history
- Reads CLAUDE.md from its own branch (may differ!)
- Has its own MEMORY.md (shared path hash — same project root)
- Can have separate MCP connections and hook configs

### Coordination Patterns

| Pattern | How | Best for |
|---------|-----|---------|
| **Feature isolation** | `/branch feature/<name>` per feature | Preventing context bleed between unrelated features |
| **PR review** | `/branch pr/<number>` from remote | Review someone's PR while you keep working on `main` |
| **CI worktree** | Script creates worktree, runs tests, deletes | Parallel CI without touching working copy |
| **Agent Teams** | Each team member agent gets a worktree | Parallel multi-agent work on different services |

## Git Worktrees vs git clone — Deep Comparison

Understanding the difference between `git worktree` and `git clone` is essential for efficient parallel Claude Code sessions. The two approaches look similar on the surface but have fundamentally different data models.

### Shared .git Database Architecture

```
GIT WORKTREE MODEL
==================

~/projects/my-project/
├── .git/                   ← ONE shared database
│   ├── objects/            ← All commit objects (shared)
│   ├── refs/               ← All branch refs (shared)
│   ├── config              ← Remotes, settings (shared)
│   └── worktrees/
│       ├── my-project-feature-auth/   ← Worktree metadata only
│       │   ├── HEAD                   ← Points to feature/auth
│       │   ├── index                  ← Staging area for this WT
│       │   └── gitdir                 ← Back-pointer
│       └── my-project-feature-ui/
│           ├── HEAD                   ← Points to feature/ui
│           ├── index
│           └── gitdir
├── (working files for main)
│
├── ../my-project-feature-auth/    ← Separate directory
│   ├── .git                       ← Single FILE (not dir) → back-pointer
│   └── (working files for feature/auth)
│
└── ../my-project-feature-ui/
    ├── .git                       ← Single FILE → back-pointer
    └── (working files for feature/ui)


GIT CLONE MODEL
===============

~/projects/my-project/          ← Full .git database #1
├── .git/
│   ├── objects/                ← DUPLICATE of all objects
│   ├── refs/
│   └── config                  ← Separate remote tracking
└── (working files)

~/projects/my-project-clone-1/  ← Full .git database #2
├── .git/
│   ├── objects/                ← ANOTHER DUPLICATE
│   ├── refs/
│   └── config
└── (working files)
```

### Side-by-Side Comparison

| Dimension | `git worktree` | `git clone` |
|-----------|---------------|-------------|
| **Disk usage** | ~0 extra (shared objects store) | Full repo size × N copies |
| **Create time** | Milliseconds | Seconds to minutes (network clone) |
| **Branch awareness** | All branches immediately visible everywhere | Must fetch in each clone |
| **Fetch/push** | One `git fetch` updates all worktrees | Must fetch independently in each clone |
| **`git log`** | Same history everywhere | Can drift if one clone doesn't fetch |
| **Stash** | Stash is per-worktree but stored in shared db | Stash is per-clone |
| **Hooks** | `.git/hooks/` shared (runs in all worktrees) | Each clone has independent hooks |
| **Submodules** | Shared, but each WT has independent checkout | Must init submodules per clone |
| **Same branch** | IMPOSSIBLE — enforced by git | Possible (risky but allowed) |
| **Claude Code context** | Fresh session per worktree, shared MEMORY.md root | Fresh session per clone, isolated MEMORY.md |
| **CLAUDE.md** | Loaded from each worktree's branch | Loaded from each clone's HEAD |
| **Cleanup** | `git worktree remove <path>` | `rm -rf <clone>` |

### Why Worktrees Are Better for Parallel Claude Code Sessions

**1. Branch Isolation is Enforced**

Git prevents two worktrees from checking out the same branch. This maps perfectly to Claude Code's mental model: one session per concern, no accidental overwrites.

```bash
# This FAILS — git protects you
git worktree add ../my-project-feature-auth main
# fatal: 'main' is already checked out at '/home/user/projects/my-project'
```

**2. Zero-Lag Context Switching**

With clones, switching Claude sessions means navigating to different directories AND potentially fetching new changes. With worktrees, Claude instantly sees every branch.

```bash
# Worktree: review PR#847 without stopping current work
git worktree add ../my-project-pr-847 origin/pr/847
cd ../my-project-pr-847
claude  # fresh session, sees pr/847 code, your main session is untouched
```

**3. Shared Remote State**

One `git fetch --all` in any worktree makes remote branches visible in all worktrees. Claude sessions in different worktrees never have a stale view of remote state.

```bash
# In main worktree — also updates all sibling worktrees' remote view
git fetch --all --prune
```

**4. Minimal Filesystem Footprint**

For large repos (50 MB–10 GB of `.git` objects), worktrees consume near-zero extra disk. A team with 5 active worktrees pays the same disk cost as 1 clone.

```bash
# Check actual disk usage
du -sh my-project/.git/               # e.g. 2.1 GB (all objects)
du -sh my-project-feature-auth/.git   # e.g.  4 KB (just a pointer file)
```

**5. CLAUDE.md Per Branch**

Each worktree checks out its own branch, so it loads the `CLAUDE.md` on that branch. This means your feature branch can have a `CLAUDE.md` tailored to the feature work in progress — e.g., temporarily adding "Focus on auth module only, skip tests for now."

## /branch Command — Complete Reference

The `/branch` command is Claude Code's high-level wrapper around `git worktree add`. It automates the full workflow from branch creation to session launch.

### Syntax

```
/branch <branch-name> [--from <base>] [--path <custom-path>] [--no-window]
```

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `<branch-name>` | string | required | Name of the new branch to create. Can include `/` (e.g. `feature/auth`). |
| `--from <base>` | string | `HEAD` | Base commit, branch, or tag to branch from. Use `--from main` to branch from latest main even if you're on a feature branch. |
| `--path <custom-path>` | string | auto-computed | Override the sibling-directory naming convention. Useful if default path conflicts with another worktree. |
| `--no-window` | flag | off | Create worktree and print path, but do NOT open a new terminal window. Useful in scripts or when using tmux/multiplexers manually. |

### What `/branch` Creates

```
BEFORE /branch feature/auth
============================
~/projects/api/              ← CWD, branch: main
  ├── .git/
  ├── src/
  └── CLAUDE.md


AFTER /branch feature/auth
===========================
~/projects/api/              ← unchanged, still on main
  ├── .git/
  │   └── worktrees/
  │       └── api-feature-auth/   ← metadata added
  ├── src/
  └── CLAUDE.md

~/projects/api-feature-auth/ ← NEW worktree
  ├── .git                   ← single file, not a dir
  ├── src/                   ← same files, different branch
  └── CLAUDE.md              ← CLAUDE.md from feature/auth branch

[NEW TERMINAL WINDOW]
  CWD: ~/projects/api-feature-auth/
  Runs: claude
  → Fresh Claude Code session starts
  → Loads CLAUDE.md from feature/auth branch
  → No knowledge of the main session
```

### Filesystem Naming Convention

`/branch` derives the worktree directory name by combining the **parent project name** with the **branch name**, replacing `/` with `-`:

| Project dir | Branch name | Worktree path |
|-------------|------------|--------------|
| `~/projects/api` | `feature/auth` | `~/projects/api-feature-auth` |
| `~/projects/api` | `hotfix/CVE-2026-1234` | `~/projects/api-hotfix-CVE-2026-1234` |
| `~/projects/api` | `pr/847` | `~/projects/api-pr-847` |
| `~/code/my-long-project-name` | `refactor/database` | `~/code/my-long-project-name-refactor-database` |

Use `--path` to override when the auto-name would be too long or conflicts with an existing directory.

### Branch Already Exists

If the branch already exists remotely or locally, `/branch` behaves as `git worktree add`:

```bash
# Branch exists locally — checks it out in new worktree
/branch existing-feature

# Branch exists only on remote — fetches and tracks it
/branch origin/pr/847 --from origin/pr/847

# Explicit: create from remote branch
/branch my-review --from origin/feature/payments
```

### Listing and Removing Worktrees

```bash
# List all active worktrees (also shows stale ones)
git worktree list
# /home/user/projects/api               abc1234 [main]
# /home/user/projects/api-feature-auth  def5678 [feature/auth]
# /home/user/projects/api-feature-ui    ghi9012 [feature/ui]

# Clean up a finished worktree
git worktree remove ../api-feature-auth

# Force-remove even if there are uncommitted changes (DESTRUCTIVE)
git worktree remove --force ../api-feature-auth

# Prune stale worktree entries (e.g. directory was deleted manually)
git worktree prune
```

## Parallel Development Patterns

These are the five most common workflows teams use when combining Git worktrees with Claude Code sessions.

### Pattern 1: Feature Isolation

**Problem**: You're building two unrelated features. Switching context in one session pollutes the conversation history and causes Claude to mix concerns.

**Solution**: One worktree per feature, one Claude session per worktree.

```
SESSION A (main worktree, branch: main)
  Claude: "I'll be your baseline. Ask me about production issues."

SESSION B (worktree: api-feature-payments, branch: feature/payments)
  Claude: "Building Stripe integration. Focused only on payments code."
  → Reads payments-specific CLAUDE.md additions
  → Context window: only payments files opened

SESSION C (worktree: api-feature-notifications, branch: feature/notifications)
  Claude: "Building email notification system."
  → Reads notification-specific context
  → Zero knowledge of payments session
```

```bash
# Setup
cd ~/projects/api
/branch feature/payments
/branch feature/notifications
# → Two new terminal windows open, each with isolated Claude session

# When features are done
git checkout main
git merge feature/payments
git merge feature/notifications
git worktree remove ../api-feature-payments
git worktree remove ../api-feature-notifications
```

### Pattern 2: PR Review While Working

**Problem**: A colleague's PR needs review, but you're mid-flow on your own work. Checking it out on `main` would lose your changes.

**Solution**: Check out the PR branch in a dedicated worktree.

```bash
# Your colleague's PR is origin/feature/new-auth-flow (PR #284)
# You're currently building something on feature/my-feature

# In your main session:
/branch pr-284 --from origin/feature/new-auth-flow
# → new worktree at ../api-pr-284
# → new Claude session opens

# In the PR review session:
# "Review this PR for security issues, performance problems, and adherence to our API conventions."

# Meanwhile — your main session is completely unaffected
# No stash, no branch switching, no lost context
```

```
TIME AXIS:
──────────────────────────────────────────────────────►
Session A (feature/my-feature):
  ████████████████████████████████████  ← uninterrupted

Session B (pr-284) ←────starts here
                    ███████  ← PR review, then closed
```

### Pattern 3: Hotfix While on a Long-Running Feature

**Problem**: Production is down. You need to push a hotfix to `main`, but you have 3 hours of uncommitted work on a feature branch.

**Solution**: Create a hotfix worktree from `main`, fix and deploy, then return to your feature.

```bash
# Production incident begins
# You're on feature/big-refactor with lots of staged/unstaged changes

# In your feature Claude session:
/branch hotfix/null-pointer-in-payment --from main
# → new terminal, new Claude session, branched from main
# → your feature session is completely untouched

# In the hotfix session:
# "There's a null pointer exception in PaymentProcessor.charge() on line 847.
#  The fix is to add a null check before calling amount.toFixed().
#  Apply the fix, run the payment tests, and prepare a commit."

# Claude fixes it, you review, you push:
git push origin hotfix/null-pointer-in-payment
# → merge to main via fast PR

# Cleanup hotfix worktree
git worktree remove ../api-hotfix-null-pointer-in-payment

# Return to feature session — everything exactly as you left it
```

```
Worktree layout during incident:
api/                          ← feature/big-refactor (your uncommitted work, SAFE)
api-hotfix-null-pointer/      ← main + hotfix commit (clean, deployable)
```

### Pattern 4: A/B Testing Two Implementations

**Problem**: Two engineers disagree on the right architecture. Instead of debating, you want to build both and measure.

**Solution**: Two worktrees, each with a different implementation, both running simultaneously.

```bash
# Approach A: Repository pattern for database access
/branch experiment/repo-pattern --from main
# → Session A builds the repository pattern implementation

# Approach B: Active Record pattern
/branch experiment/active-record --from main
# → Session B builds the active record implementation

# Both sessions run their implementations' test suites simultaneously
# Compare results, pick winner, discard loser

# Cleanup
git worktree remove ../api-experiment-repo-pattern
git worktree remove ../api-experiment-active-record
```

```
api-experiment-repo-pattern/   api-experiment-active-record/
  Claude: "Implementing          Claude: "Implementing
  Repository pattern..."         Active Record pattern..."
  → Runs: npm test               → Runs: npm test
  → Result: 847ms avg            → Result: 234ms avg
                                             ↑ winner
```

### Pattern 5: Concurrent Refactoring of Independent Modules

**Problem**: A large refactor touches 5 independent modules. Sequential refactoring would take a week. The modules don't depend on each other mid-refactor.

**Solution**: Fan out — one worktree per module, all running Claude sessions in parallel.

```bash
# Create worktrees for each module
/branch refactor/auth-module      --from main
/branch refactor/payment-module   --from main
/branch refactor/notification-module --from main
/branch refactor/reporting-module --from main
/branch refactor/admin-module     --from main
# → Five terminal windows, five Claude sessions

# Each session receives a focused instruction:
# "Refactor the auth module to use the new ServiceContainer pattern.
#  Follow the patterns in CLAUDE.md section 'Dependency Injection'.
#  Only touch files under src/auth/. Run tests after each file."
```

```
Timeline with parallel worktrees vs sequential:
                                                   
SEQUENTIAL (1 session):                             
  auth   ████████                                   
  payment        ████████                           
  notif                  ████████                   
  report                         ████████           
  admin                                  ████████   
  Total: 5 days                                     
                                                    
PARALLEL (5 worktrees):                             
  auth   ████████                                   
  payment████████                                   
  notif  ████████                                   
  report ████████                                   
  admin  ████████                                   
  Total: 1 day ← 5x faster                         
```

After all sessions complete:

```bash
# Merge results sequentially (each module is independent, no conflicts)
git checkout main
git merge refactor/auth-module
git merge refactor/payment-module
git merge refactor/notification-module
git merge refactor/reporting-module
git merge refactor/admin-module

# Clean up all worktrees
for module in auth payment notification reporting admin; do
  git worktree remove "../api-refactor-${module}-module"
done
```

## SDK-Driven Parallel Worktrees

For automated pipelines, CI systems, or orchestration scripts, you can manage multiple worktree Claude Code sessions programmatically using the Claude Code SDK.

### Python: Parallel Worktree Manager

```python
"""
parallel_worktrees.py — Orchestrate multiple Claude Code sessions
across git worktrees for concurrent, isolated work.
"""
import asyncio
import subprocess
import os
from pathlib import Path
import anthropic

# Claude Code SDK client
client = anthropic.Anthropic()

async def create_worktree(repo_root: Path, branch: str, base: str = "main") -> Path:
    """Create a git worktree and return its path."""
    # Derive sibling path from branch name (mirrors /branch command behaviour)
    safe_branch = branch.replace("/", "-")
    worktree_path = repo_root.parent / f"{repo_root.name}-{safe_branch}"

    subprocess.run(
        ["git", "worktree", "add", "-b", branch, str(worktree_path), base],
        cwd=repo_root,
        check=True,
        capture_output=True,
    )
    print(f"Created worktree: {worktree_path} (branch: {branch})")
    return worktree_path


async def remove_worktree(repo_root: Path, worktree_path: Path) -> None:
    """Remove a git worktree after work is complete."""
    subprocess.run(
        ["git", "worktree", "remove", str(worktree_path)],
        cwd=repo_root,
        check=True,
        capture_output=True,
    )
    print(f"Removed worktree: {worktree_path}")


async def run_claude_in_worktree(
    worktree_path: Path,
    task: str,
    model: str = "claude-sonnet-4-6",
) -> dict:
    """
    Run a Claude Code SDK session in a specific worktree directory.
    Returns a dict with branch, output, and success status.
    """
    branch = subprocess.check_output(
        ["git", "branch", "--show-current"],
        cwd=worktree_path,
        text=True,
    ).strip()

    print(f"Starting Claude session in {branch}...")

    messages = []
    result_text = []

    # Use the SDK in subprocess mode — set CWD to the worktree
    # Claude Code reads CLAUDE.md from the worktree's branch
    with client.messages.stream(
        model=model,
        max_tokens=8096,
        system=f"You are working in git worktree: {worktree_path}. "
               f"Current branch: {branch}. "
               f"Only touch files relevant to the assigned task. "
               f"Run tests after making changes.",
        messages=[{"role": "user", "content": task}],
    ) as stream:
        for text in stream.text_stream:
            result_text.append(text)

    return {
        "branch": branch,
        "worktree": str(worktree_path),
        "output": "".join(result_text),
        "success": True,
    }


async def parallel_refactor(repo_root: Path, modules: list[dict]) -> list[dict]:
    """
    Fan out a refactoring task across multiple worktrees in parallel.

    modules: list of {"branch": "refactor/auth", "task": "Refactor the auth module..."}
    """
    # Step 1: Create all worktrees
    worktree_paths = await asyncio.gather(*[
        create_worktree(repo_root, m["branch"])
        for m in modules
    ])

    # Step 2: Run Claude sessions in parallel
    results = await asyncio.gather(*[
        run_claude_in_worktree(path, m["task"])
        for path, m in zip(worktree_paths, modules)
    ])

    # Step 3: Clean up worktrees
    for path in worktree_paths:
        await remove_worktree(repo_root, path)

    return results


# Example usage
async def main():
    repo = Path("/home/user/projects/api")

    modules = [
        {
            "branch": "refactor/auth-module",
            "task": "Refactor src/auth/ to use ServiceContainer DI pattern. "
                    "Run npm test -- --testPathPattern=auth after changes.",
        },
        {
            "branch": "refactor/payment-module",
            "task": "Refactor src/payments/ to use ServiceContainer DI pattern. "
                    "Run npm test -- --testPathPattern=payment after changes.",
        },
        {
            "branch": "refactor/notification-module",
            "task": "Refactor src/notifications/ to use ServiceContainer DI pattern. "
                    "Run npm test -- --testPathPattern=notification after changes.",
        },
    ]

    results = await parallel_refactor(repo, modules)

    for r in results:
        status = "SUCCESS" if r["success"] else "FAILED"
        print(f"\n[{status}] {r['branch']}")
        print(r["output"][:500] + "..." if len(r["output"]) > 500 else r["output"])


if __name__ == "__main__":
    asyncio.run(main())
```

### TypeScript: Worktree Session Orchestrator

```typescript
/**
 * worktree-orchestrator.ts
 * Manage parallel Claude Code SDK sessions across git worktrees.
 */
import { execSync, execFileSync } from "child_process";
import * as path from "path";
import * as fs from "fs";
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

interface WorktreeTask {
  branch: string;
  task: string;
  model?: string;
}

interface WorktreeResult {
  branch: string;
  worktreePath: string;
  output: string;
  success: boolean;
  error?: string;
}

function createWorktree(repoRoot: string, branch: string, base = "main"): string {
  const safeBranch = branch.replace(/\//g, "-");
  const parentDir = path.dirname(repoRoot);
  const repoName = path.basename(repoRoot);
  const worktreePath = path.join(parentDir, `${repoName}-${safeBranch}`);

  execFileSync("git", ["worktree", "add", "-b", branch, worktreePath, base], {
    cwd: repoRoot,
    stdio: "pipe",
  });

  console.log(`Created worktree: ${worktreePath}`);
  return worktreePath;
}

function removeWorktree(repoRoot: string, worktreePath: string): void {
  execFileSync("git", ["worktree", "remove", worktreePath], {
    cwd: repoRoot,
    stdio: "pipe",
  });
  console.log(`Removed worktree: ${worktreePath}`);
}

async function runClaudeInWorktree(
  worktreePath: string,
  task: string,
  model = "claude-sonnet-4-6"
): Promise<WorktreeResult> {
  const branch = execSync("git branch --show-current", {
    cwd: worktreePath,
    encoding: "utf8",
  }).trim();

  console.log(`Starting Claude session for branch: ${branch}`);

  try {
    const chunks: string[] = [];

    const stream = await client.messages.stream({
      model,
      max_tokens: 8096,
      system:
        `You are working in git worktree: ${worktreePath}. ` +
        `Current branch: ${branch}. ` +
        `Only modify files relevant to your assigned task. ` +
        `Run tests after making changes and report results.`,
      messages: [{ role: "user", content: task }],
    });

    for await (const chunk of stream) {
      if (
        chunk.type === "content_block_delta" &&
        chunk.delta.type === "text_delta"
      ) {
        chunks.push(chunk.delta.text);
      }
    }

    return {
      branch,
      worktreePath,
      output: chunks.join(""),
      success: true,
    };
  } catch (error) {
    return {
      branch,
      worktreePath,
      output: "",
      success: false,
      error: error instanceof Error ? error.message : String(error),
    };
  }
}

async function parallelWorktreeSessions(
  repoRoot: string,
  tasks: WorktreeTask[]
): Promise<WorktreeResult[]> {
  // Create all worktrees first
  const worktreePaths = tasks.map((t) => createWorktree(repoRoot, t.branch));

  // Run all Claude sessions in parallel
  const results = await Promise.all(
    tasks.map((task, i) =>
      runClaudeInWorktree(worktreePaths[i], task.task, task.model)
    )
  );

  // Cleanup
  worktreePaths.forEach((p) => removeWorktree(repoRoot, p));

  return results;
}

// Example: fan-out security audit across services
async function main() {
  const repoRoot = "/home/user/projects/my-app";

  const auditTasks: WorktreeTask[] = [
    {
      branch: "audit/auth-service",
      task: "Perform a security audit of services/auth/. Check for: SQL injection, improper JWT validation, missing rate limits, insecure direct object references. Report findings as a structured list.",
      model: "claude-opus-4-7",
    },
    {
      branch: "audit/payment-service",
      task: "Perform a security audit of services/payments/. Focus on: PCI-DSS compliance, card data handling, webhook signature validation, idempotency key usage.",
      model: "claude-opus-4-7",
    },
    {
      branch: "audit/api-gateway",
      task: "Audit services/gateway/ for: authentication bypass vectors, CORS misconfiguration, request smuggling vulnerabilities, missing security headers.",
      model: "claude-opus-4-7",
    },
  ];

  console.log(`Running ${auditTasks.length} parallel security audits...`);
  const results = await parallelWorktreeSessions(repoRoot, auditTasks);

  for (const result of results) {
    console.log(`\n${"=".repeat(60)}`);
    console.log(`Branch: ${result.branch}`);
    console.log(`Status: ${result.success ? "COMPLETED" : "FAILED"}`);
    if (result.error) console.log(`Error: ${result.error}`);
    console.log(`\nFindings:\n${result.output.slice(0, 1000)}...`);
  }
}

main().catch(console.error);
```

### CI Pipeline Integration (GitHub Actions)

```yaml
# .github/workflows/parallel-claude-review.yml
name: Parallel Claude Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  setup-worktrees:
    runs-on: ubuntu-latest
    outputs:
      changed-services: ${{ steps.detect.outputs.services }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # full history for worktree support

      - id: detect
        run: |
          SERVICES=$(git diff --name-only origin/main...HEAD \
            | grep '^services/' \
            | cut -d/ -f2 \
            | sort -u \
            | jq -R -s -c 'split("\n")[:-1]')
          echo "services=$SERVICES" >> $GITHUB_OUTPUT

  claude-review:
    needs: setup-worktrees
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: ${{ fromJson(needs.setup-worktrees.outputs.changed-services) }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Create worktree for ${{ matrix.service }}
        run: |
          git worktree add ../review-${{ matrix.service }} \
            origin/pr/${{ github.event.pull_request.number }}

      - name: Run Claude Code review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          cd ../review-${{ matrix.service }}
          claude --output-format json \
            --bare \
            -p "Review changes in services/${{ matrix.service }}/ for correctness,
                performance issues, and adherence to CLAUDE.md conventions.
                Output a structured JSON report." \
            > review-${{ matrix.service }}.json

      - name: Upload review artifact
        uses: actions/upload-artifact@v4
        with:
          name: review-${{ matrix.service }}
          path: ../review-${{ matrix.service }}/review-${{ matrix.service }}.json
```

## Team Coordination

When multiple engineers on a team use Claude Code with worktrees, consistent coordination conventions prevent conflicts and maximise the benefits of parallel work.

### Worktree Naming Conventions

Agree on a team-wide naming convention so worktrees are immediately identifiable:

```
RECOMMENDED CONVENTION
======================

Feature work:     {project}-feature-{ticket-id}-{short-desc}
                  api-feature-PLAT-1847-oauth-refresh

Hotfixes:         {project}-hotfix-{ticket-id}
                  api-hotfix-INC-2026-0603-payment-null

PR review:        {project}-pr-{number}
                  api-pr-284

Experiments:      {project}-exp-{description}
                  api-exp-postgres-vs-sqlite-perf

CI/automated:     {project}-ci-{job-id}
                  api-ci-48291-security-audit
```

### Shared vs Isolated CLAUDE.md

The most powerful team pattern is layering `CLAUDE.md` files so they compose correctly:

```
SHARED (checked into main — everyone inherits)
==============================================
CLAUDE.md                    ← company-wide: security rules, commit format,
                               PR template, review checklist

services/api/CLAUDE.md       ← API team: REST conventions, error handling,
                               authentication patterns

services/api/src/auth/CLAUDE.md ← Auth subsystem: JWT specifics, session
                                  management rules


BRANCH-LOCAL (not merged to main — temporary, session-specific)
===============================================================
CLAUDE.md additions on feature/oauth-refresh:
  "Focus only on src/auth/oauth/ directory.
   The OAuthProvider interface is being refactored — do not touch
   the old src/auth/legacy/ path.
   Temporary: skip flaky integration test suite during this sprint."
```

### Avoiding Cross-Worktree Conflicts

```
CONFLICT RISK MAP
=================

HIGH RISK — files touched by many worktrees:
  package.json, package-lock.json    ← coordinate via a "deps" session
  prisma/schema.prisma               ← serialise DB migrations
  src/types/global.d.ts              ← shared type changes need merge coordination

MEDIUM RISK — shared but less frequent:
  .env.example                       ← add env vars in batches
  tsconfig.json                      ← architecture-level changes only
  CLAUDE.md (root)                   ← treat like docs: PR + review

LOW RISK — each worktree owns its space:
  services/auth/**                   ← auth worktree
  services/payments/**               ← payments worktree
  services/frontend/**               ← frontend worktree
```

**Rule of thumb**: assign file ownership to worktrees the same way you'd assign ownership to engineers. If two worktrees need to touch the same file, coordinate via a shared branch or serialise the merges.

Use a lightweight shared markdown file to coordinate which sessions are active:


### Claude Code Configuration for Worktrees

Add to your project's root `.claude/settings.json` to configure worktree-aware defaults:

```json
{
  "worktrees": {
    "autoCleanup": true,
    "namingConvention": "{project}-{branch-sanitized}",
    "defaultBase": "main",
    "openNewWindow": true
  },
  "hooks": {
    "PostWorktreeCreate": [
      {
        "command": "bash .claude/scripts/worktree-init.sh $CLAUDE_WORKTREE_PATH",
        "description": "Initialise worktree: install deps, set env vars"
      }
    ]
  }
}
```

```bash
# .claude/scripts/worktree-init.sh
#!/usr/bin/env bash
# Called after /branch creates a new worktree
WORKTREE="$1"

echo "Initialising worktree at $WORKTREE..."

# Copy .env.local (gitignored, not in branch)
if [ -f ".env.local" ]; then
  cp .env.local "$WORKTREE/.env.local"
fi

# Install dependencies if package.json differs from main
cd "$WORKTREE"
if ! diff -q package.json ../$(basename $(git rev-parse --show-toplevel))/package.json > /dev/null 2>&1; then
  npm install
fi

echo "Worktree ready."
```
