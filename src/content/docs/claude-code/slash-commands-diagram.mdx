### Custom Command Anatomy

```markdown
<!-- .claude/commands/deploy.md -->
---
description: Deploy the current service to staging
allowed-tools: Bash, Read
---

# Deploy to Staging

## Context
Current branch: !`git branch --show-current`
Service: $ARGUMENTS

## Steps
@import standards/deploy-checklist.md

Run the deployment for the {{service}} service:
...
```

| Variable | Resolves to |
|----------|------------|
| `$ARGUMENTS` | Text typed after the command: `/deploy api-service` → `api-service` |
| `!` prefix | Shell command output: `` !`git log --oneline -5` `` → last 5 commits |
| `@import path` | Contents of another file inserted inline |
| `{{var}}` | Prompt Claude to substitute (not built-in — Claude interprets) |

### Personal vs Project Commands

| Scope | Path | Git? | Visible to |
|-------|------|------|-----------|
| Personal | `~/.claude/commands/<name>.md` | No | Only you, all projects |
| Project | `.claude/commands/<name>.md` | Yes | All team members on this project |
| Plugin | `~/.claude/plugins/<name>/commands/` | Via plugin | Plugin users |

### Invocation

```
> /deploy api-service      ← project command with argument
> /my-standup              ← personal command, no argument
> /deploy<tab>             ← tab completion shows description
```

## Custom Command Frontmatter Reference

Every custom command file (`.claude/commands/<name>.md` or `~/.claude/commands/<name>.md`) supports the following frontmatter keys:

```markdown
---
name: my-command
description: What this command does (shown in /help and tab completion)
allowed-tools: [Bash(git:*), Read, Edit]
argument-hint: [message]
model: claude-haiku-4-5
context: fork
disable-model-invocation: false
---
```

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `name` | string | filename | The `/name` used to invoke the command (no spaces) |
| `description` | string | — | One-line description shown in `/help` and tab completion |
| `allowed-tools` | list | all | Tool allowlist scoped to this command only; narrows global permissions |
| `argument-hint` | list | — | Placeholder text shown after the command name in the UI prompt |
| `model` | string | session default | Override the model for this command only |
| `context` | `fork` or `inherit` | `inherit` | `fork` starts a fresh context window; `inherit` continues the current session |
| `disable-model-invocation` | boolean | `false` | If `true`, execute as a pure prompt template — no LLM call, just expand variables |

## Special Variables Reference

| Variable | What it expands to | Example |
|----------|--------------------|---------|
| `$ARGUMENTS` | Everything typed after the command name | `/commit "feat: add auth"` → `"feat: add auth"` |
| `$1`, `$2`, ... | Positional arguments split by whitespace | `/greet Alice Bob` → `$1 = "Alice"`, `$2 = "Bob"` |
| `${CLAUDE_EFFORT}` | Current effort level setting | `low`, `normal`, `high`, `xhigh` |
| `${CLAUDE_MODEL}` | Active model ID for the session | `claude-sonnet-4-6` |
| `@path/to/file.md` | Inline contents of the file at that path | File is read and its text is inserted at that point in the prompt |
| `` !`shell command` `` | Output of the shell command, captured at invocation time | `` !`git log --oneline -5` `` → last 5 commit lines |
| `{{placeholder}}` | Claude is prompted to fill this in before executing | `{{target environment}}` → Claude asks "Which environment?" |

## Command Scope Resolution Order

When you type a command, Claude Code resolves it in this order (first match wins):

```
1. Plugin commands     (~/.claude/plugins/<name>/commands/)
   └─ highest priority; plugins can override built-ins

2. Project commands    (.claude/commands/<name>.md)
   └─ committed to the repo; shared with the whole team

3. Personal commands   (~/.claude/commands/<name>.md)
   └─ your private commands; not in version control

4. Built-in commands   (compiled into Claude Code binary)
   └─ lowest priority; overridable by all above
```

This means a project-level `/review` command will shadow the built-in `/review` for everyone on that project. A personal command shadows both built-ins and is shadowed by plugins.

## Practical Custom Command Examples

### Example 1: Commit with conventional message

```markdown
<!-- .claude/commands/commit.md -->
---
description: Stage all changes and commit with a conventional message
allowed-tools: [Bash(git:*), Read]
argument-hint: [scope] [message]
---

Stage and commit all uncommitted changes.

Current git status:
!`git status --short`

Recent commits for style reference:
!`git log --oneline -5`

Write a conventional commit message following the pattern `type(scope): description`.
The scope is "$1" and the message hint is "$2".
Use the actual diff to determine the type (feat/fix/refactor/chore/docs/test).

Then run:
```bash
git add -A && git commit -m "<your message>"
```
```

Invoke with: `/commit auth "add JWT refresh token support"`

### Example 2: PR review checklist

```markdown
<!-- .claude/commands/pr-check.md -->
---
description: Review a PR branch against main and report issues
allowed-tools: [Bash(git:*), Read, Glob, Grep]
argument-hint: [branch-name]
---

Review the branch "$ARGUMENTS" against main.

Diff to review:
!`git diff main...$ARGUMENTS`

Files changed:
!`git diff --name-only main...$ARGUMENTS`

Check for:
1. Missing tests for any new functions or exported symbols
2. Hardcoded secrets, tokens, or credentials (look for sk-, ghp_, AWS patterns)
3. Any TODO or FIXME comments introduced (not pre-existing)
4. Functions longer than 50 lines without a clear decomposition reason
5. Missing error handling on async operations

Report each issue as: `[SEVERITY] file:line — description`
Severity: BLOCKER | MAJOR | MINOR | NIT
```

Invoke with: `/pr-check feature/add-oauth`

### Example 3: Service-scoped deployment helper

```markdown
<!-- services/payments/.claude/commands/deploy-staging.md -->
---
description: Deploy the payments service to staging and run smoke tests
allowed-tools: [Bash(git:*), Bash(npm:*), Bash(docker:*), Read]
model: claude-haiku-4-5
context: fork
---

Deploy the payments service to staging.

Pre-flight checks:
!`git branch --show-current`
!`npm test -- --silent 2>&1 | tail -5`

If tests pass, run:
```bash
docker build -t payments:staging .
docker push registry.corp.com/payments:staging
kubectl set image deployment/payments payments=registry.corp.com/payments:staging -n staging
kubectl rollout status deployment/payments -n staging --timeout=120s
```

After deployment completes, run the smoke test suite:
```bash
npm run test:smoke -- --env staging
```

Report: deployment status, rollout time, and smoke test results.
```

Invoke with: `/deploy-staging` from inside the `services/payments/` directory.

## Custom Command Anatomy — Complete Frontmatter Reference

Custom commands live in `.claude/commands/<name>.md` (project) or `~/.claude/commands/<name>.md` (personal).

Every field in the YAML frontmatter:

```yaml
---
name: my-command          # Required: name after / (no spaces, no /)
description: >            # Required: shown in /help and autocomplete picker
  One-paragraph description of what this command does.
  Keep under 500 chars for clean autocomplete display.
allowed-tools:            # Optional: restrict which tools this command can use
  - Read
  - Bash
  - Edit
confirmation-required: true   # Optional: show "Are you sure?" before running
hide: false               # Optional: hide from /help listing (still invocable)
---

Command content goes here. Use $ARGUMENTS for inline substitution.
```

**Special variables available in command content:**

| Variable | Resolves to |
|----------|------------|
| `$ARGUMENTS` | Everything after the command name (e.g. `/my-command foo bar` → `foo bar`) |
| `$ARG_1`, `$ARG_2` | Space-split individual arguments |
| `$(shell command)` | Execute shell command and inline its stdout |
| `@./path/to/file.md` | Inline the content of a file at that path |
| `$CLAUDE_CWD` | Current working directory |
| `$CLAUDE_SESSION_ID` | Unique ID for the current session |

## Argument Parsing Deep Dive

### `$ARGUMENTS` — Full Verbatim Capture

```markdown
# .claude/commands/summarize.md
---
name: summarize
description: Summarize a file in 3 bullet points
---

Summarize the file at `$ARGUMENTS` in 3 bullet points.
Focus on: purpose, key functions, side effects.
```

Usage: `/summarize src/auth/login.ts`
→ Claude sees: `Summarize the file at src/auth/login.ts in 3 bullet points.`

### Positional Arguments: `$ARG_1`, `$ARG_2`...

```markdown
# .claude/commands/refactor.md
Refactor the function `$ARG_1` in `$ARG_2`.
Goal: $ARG_3
```

Usage: `/refactor processPayment src/payments.ts improve error handling`
→ `$ARG_1=processPayment`, `$ARG_2=src/payments.ts`, `$ARG_3=improve error handling`

### Shell Execution in Commands

```markdown
# .claude/commands/git-summary.md
Summarize changes across the last $(git log --oneline -10 | wc -l) commits.
Log: $(git log --oneline -10)
Branch: $(git branch --show-current)
Changed files: $(git diff --name-only HEAD~1)
```

Shell commands run at invocation time, not at load time — commands are always dynamic.

### Optional Argument Defaults

```markdown
Run tests for the `${ARG_1:-all services}` suite.
```

Usage: `/test-service` → `all services` | `/test-service auth` → `auth`
