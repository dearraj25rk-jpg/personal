## Permissions Quick Reference

### Four Permission Layers

From highest to lowest precedence:

| Layer | File | Who controls | Override? |
|-------|------|-------------|----------|
| Enterprise Managed | `~/.claude/managed-settings.json` | MDM/IT admin | Cannot be overridden |
| Project Local | `.claude/settings.local.json` | Individual dev | Overrides project + user |
| Project | `.claude/settings.json` | Team (committed) | Overrides user settings |
| User Global | `~/.claude/settings.json` | Individual dev | Base defaults |

### Permission Modes

| Mode | `--permission-mode` flag | What it does |
|------|------------------------|-------------|
| `default` | (none) | Prompts for each new tool permission |
| `acceptEdits` | `--permission-mode acceptEdits` | Auto-approves file edits, prompts for Bash |
| `bypassPermissions` | `--permission-mode bypassPermissions` | Skips ALL permission checks — use in sandboxed CI only |
| `autoApprove` | `--permission-mode autoApprove` | Approves everything including dangerous operations |

> **CI recommendation:** Use `--permission-mode bypassPermissions` only inside Docker containers or restricted CI environments where the filesystem scope is already constrained at the container level.

### Tool Allowlist / Blocklist Syntax

```json
// .claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(npm:*)",           // allow npm commands
      "Bash(git:*)",           // allow all git commands
      "Read",                  // allow all file reads
      "Edit(.claude/**)"       // allow edits only in .claude/
    ],
    "deny": [
      "Bash(rm:-rf*)",         // block rm -rf
      "Bash(curl:*)",          // block all curl
      "WebFetch",              // block all web fetches
      "Write(/etc/**)"         // block writes to /etc/
    ]
  }
}
```

### Sandbox Architecture

Claude Code uses OS-level sandboxing:

| Platform | Sandbox tech | What it restricts |
|----------|-------------|-----------------|
| macOS | Seatbelt (sandbox-exec) | Filesystem paths, network, process spawning |
| Linux | bubblewrap (bwrap) | Mount namespaces, user namespaces, network |

The sandbox is applied to **Bash tool executions** when sandbox mode is enabled. File tools (Read, Write, Edit) are controlled via the allowlist, not the OS sandbox.

## Permission Modes — Precise Definitions

### `normal` (default)

Claude prompts the user before using any tool that is not explicitly allowed in the `permissions.allow` list. Read-only operations (Read, Glob, Grep) are permitted without a prompt. All write and execute operations require interactive approval unless pre-listed.

**When to use:** Interactive development sessions where the developer reviews each action. The safest default for any environment where a human is present.

```bash
claude                           # normal mode (default)
claude --permission-mode normal  # explicit
```

### `autoAccept` (acceptEdits)

Auto-approves file edits (Write, Edit, MultiEdit) and most Bash commands. Claude still prompts for sensitive operations (network calls, git push, package installation) unless those are in the `allow` list. Equivalent to the interactive "auto-accept edits" toggle.

**When to use:** Rapid iteration when you trust Claude's output and want to skip per-edit approvals. Still retains prompts for high-risk operations.

```bash
claude --permission-mode acceptEdits
```

### `bypassPermissions`

Skips ALL permission checks — no prompts, no allow/deny list evaluation. Every tool call is executed unconditionally. This mode requires the `--dangerously-skip-permissions` flag acknowledgment and should only run inside a container or VM where blast radius is constrained at the infrastructure level.

**When to use:** CI/CD pipelines running inside isolated Docker containers, sandboxed test environments, or ephemeral VMs. Never on a developer workstation.

```bash
claude --permission-mode bypassPermissions
# Typically set in CI via environment instead:
export CLAUDE_CODE_PERMISSION_MODE=bypassPermissions
```

> Managed-settings can block this mode entirely: set `disableBypassPermissionsMode: true` in `~/.claude/managed-settings.json`.

### `plan`

Claude can read and reason about files (Read, Glob, Grep, LS) but cannot write, edit, or execute anything. Equivalent to a "read-only audit" mode. No file is modified, no command is run.

**When to use:** Code review, architecture exploration, or security auditing sessions where you want Claude's analysis without any risk of side-effects.

```bash
claude --permission-mode plan
```

## Tool Allowlist / Blocklist — Full Syntax Reference

Rules are evaluated in order: `deny` wins over `allow` when both match the same tool call.

```json
{
  "permissions": {
    "allow": [
      "Read(**)",
      "Edit(**/*.ts)",
      "Bash(git:*)",
      "Bash(npm test)",
      "Bash(npm run *)"
    ],
    "deny": [
      "Bash(rm -rf*)",
      "Bash(git push --force*)",
      "WebFetch",
      "Read(**/.env*)"
    ]
  }
}
```

### Pattern syntax

| Pattern | Matches |
|---------|---------|
| `Read` | All Read calls, any path |
| `Read(**)` | All Read calls (explicit glob) |
| `Read(src/**)` | Reads inside `src/` only |
| `Edit(**/*.ts)` | Edits to `.ts` files anywhere |
| `Bash(git:*)` | Any Bash call whose command starts with `git` |
| `Bash(npm test)` | Exactly `npm test` |
| `Bash(npm run *)` | Any `npm run <script>` |
| `Bash(rm -rf*)` | Any `rm -rf` invocation |
| `WebFetch` | All WebFetch calls, any URL |
| `WebFetch(https://api.corp.com/*)` | WebFetch to that domain only |
| `mcp__github__*` | Any GitHub MCP tool |

### Deny list best practices

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf*)",
      "Bash(git push --force*)",
      "Bash(git push --force-with-lease*)",
      "Bash(curl * | bash*)",
      "Bash(wget * | bash*)",
      "Bash(npm publish*)",
      "Bash(pip install*)",
      "WebFetch",
      "Read(**/.env*)",
      "Read(**/*.pem)",
      "Read(**/*.key)"
    ]
  }
}
```

## Sandbox Architecture

Claude Code uses OS-level process sandboxing to constrain what Bash tool executions can do, independent of the allowlist.

### macOS — Apple Seatbelt (`sandbox-exec`)

The Seatbelt profile restricts the shell process spawned by the Bash tool to a narrowly defined set of allowed operations:

| Restriction | Default sandbox behavior |
|-------------|--------------------------|
| Filesystem reads | Allowed inside the project working directory only |
| Filesystem writes | Blocked outside the project working directory |
| Network | Blocked unless explicitly permitted |
| Process spawning | Allowed for child processes within the same sandbox |
| IPC / Mach ports | Blocked (no inter-process communication to other apps) |
| Camera / microphone | Blocked |

Enable with:
```bash
claude --sandbox
# or in settings.json:
# { "sandbox": true }
```

### Linux — bubblewrap (`bwrap`)

bubblewrap creates a lightweight container around the Bash tool execution using Linux kernel namespaces:

| Namespace | What it isolates |
|-----------|-----------------|
| Mount namespace | Hides host filesystem paths outside the project directory |
| User namespace | Runs as unprivileged UID inside the sandbox |
| Network namespace | No network access by default |
| PID namespace | Process tree is isolated from host PIDs |
| IPC namespace | No shared memory or semaphores with host processes |

```bash
# Linux sandbox requires bubblewrap installed:
sudo apt install bubblewrap   # Debian/Ubuntu
sudo dnf install bubblewrap   # Fedora/RHEL

# Then enable:
claude --sandbox
```

> The sandbox applies to **Bash tool executions only**. File tools (Read, Write, Edit, Glob, Grep) are controlled by the allowlist system, not the OS sandbox, because they run inside the Claude Code process itself.

## Enterprise Managed Permission Controls

These settings in `~/.claude/managed-settings.json` (or MDM-pushed equivalent) override all user and project settings:

| Key | Type | What it enforces |
|-----|------|-----------------|
| `disableBypassPermissionsMode` | `boolean` | Prevents `--permission-mode bypassPermissions` from being used on this device |
| `allowManagedHooksOnly` | `boolean` | Blocks any hooks not deployed via MDM; only IT-approved hook scripts run |
| `allowedMcpServers` | `string[]` | Allowlist of MCP server IDs; all others are silently blocked |
| `permissions.deny` | `string[]` | Global deny rules applied before any project or user allow rules |
| `permissions.allow` | `string[]` | Global allow rules that cannot be removed by project settings |

### Example managed-settings.json for a regulated environment

```json
{
  "disableBypassPermissionsMode": true,
  "allowManagedHooksOnly": true,
  "allowedMcpServers": ["github", "linear", "internal-jira"],
  "permissions": {
    "deny": [
      "WebFetch",
      "Bash(curl*)",
      "Bash(wget*)",
      "Read(**/.env*)",
      "Read(**/*.pem)",
      "Read(**/*.key)"
    ]
  }
}
```

## Audit Logging Flow

Every tool call that Claude Code evaluates — whether permitted, denied, or user-confirmed — generates an audit event.

### What gets logged

| Field | Description | Example |
|-------|-------------|---------|
| `ts` | ISO-8601 timestamp | `"2026-06-03T14:22:11Z"` |
| `user` | Developer identity (from auth) | `"alice@corp.com"` |
| `session` | Session UUID | `"sess_abc123"` |
| `tool` | Tool name | `"Bash"`, `"Edit"`, `"WebFetch"` |
| `input` | Tool arguments | `"npm test"`, `"src/auth.ts"` |
| `permitted` | Whether the call was allowed | `true`, `false` |
| `mode` | Active permission mode | `"normal"`, `"bypassPermissions"` |
| `duration_ms` | Execution time | `4201` |
| `denied_reason` | Why it was blocked (if applicable) | `"matches deny rule: Bash(rm -rf*)"` |

### Where it goes

Configure `auditLogDestination` in managed-settings or project settings:

```json
{
  "auditLogDestination": "/var/log/claude/audit.jsonl"
}
```

| Destination type | URI format | Notes |
|----------------|------------|-------|
| Local file | `/absolute/path/audit.jsonl` | JSONL, one event per line |
| Webhook / SIEM | `https://splunk.corp.com:8088/...` | JSON POST per event |
| OpenTelemetry | `otlp+http://otel-collector:4318` | OTLP spans with Claude attributes |

### OpenTelemetry integration

```json
{
  "auditLogDestination": "otlp+http://otel-collector.infra.svc.cluster.local:4318",
  "auditLogOtelResource": {
    "service.name": "claude-code",
    "deployment.environment": "production",
    "team": "payments"
  }
}
```

Events flow: Claude Code → OTLP Collector → your backend (Datadog, Honeycomb, Grafana Tempo, Jaeger).

Each permitted Bash execution creates a span. Denied calls generate a span with `error: true` and the deny reason in attributes. This lets you build dashboards and alerts for blocked operations in your existing observability stack.

## Trust Model

Claude Code's trust model distinguishes what is trusted implicitly from what requires explicit permission grant.

### Trusted by default (no prompt required)

- Reading files in the current working directory tree
- Running Glob and Grep searches within the project
- Reading environment variables (not writing)
- Calling MCP tools that are in the active `allowedMcpServers` list
- Tool calls that match an `allow` rule in any active settings layer

### Requires explicit user approval (prompt shown)

- Writing or editing files not covered by an `allow` rule
- Running Bash commands not covered by an `allow` rule
- Calling WebFetch to external URLs
- Using MCP tools not in the `allowedMcpServers` list
- Operations where the active `deny` list matches (these are blocked outright, not prompted)

### Trust model flow

```
Tool call received
       │
       ▼
Does a DENY rule match?  ──yes──► Blocked immediately (logged, no prompt)
       │ no
       ▼
Does an ALLOW rule match? ──yes──► Permitted immediately (logged, no prompt)
       │ no
       ▼
Is permission mode bypassPermissions? ──yes──► Permitted (logged, no prompt)
       │ no
       ▼
Prompt the user ──approve──► Permitted (logged, rule optionally saved)
               └─deny──► Blocked (logged)
```

This layered evaluation means MDM-pushed deny rules always win regardless of what any project or user settings allow.

## Per-Tool Permission Requirements

Not all tools require explicit permission. Here is the complete table of built-in tools and their default permission behavior:

| Tool | Default permission | Can be in allow list | Can be in deny list | Notes |
|------|-------------------|---------------------|--------------------|----|
| `Read` | Allowed (project dir) | Yes | Yes | Outside project dir requires approval |
| `Glob` | Allowed (project dir) | Yes | Yes | Search only; no write access |
| `Grep` | Allowed (project dir) | Yes | Yes | Search only; no write access |
| `Write` | Prompts | Yes | Yes | Always prompts unless allowlisted |
| `Edit` | Prompts | Yes | Yes | Always prompts unless allowlisted |
| `MultiEdit` | Prompts | Yes | Yes | Same as Edit, multiple changes |
| `Bash` | Prompts (per-command) | Yes (pattern) | Yes (pattern) | Most granular — allow `Bash(git:*)` |
| `Task` | Allowed | Yes | Yes | Subagent spawning |
| `WebFetch` | Prompts | Yes (URL pattern) | Yes | `WebFetch(https://api.example.com:*)` |
| `WebSearch` | Prompts | Yes | Yes | Prompts first time |
| `ToolSearch` | Allowed | N/A | Yes | Deferred tool schema loading |
| `Monitor` | Allowed | Yes | Yes | Background process streaming |
| MCP tools | Prompts (first use) | Yes (tool pattern) | Yes | `mcp__github__*` pattern syntax |

### Bash Permission Granularity

The `Bash` tool supports the most granular allowlist patterns:

```json
{
  "permissions": {
    "allow": [
      "Bash(git:*)",             // All git commands
      "Bash(npm run:*)",         // npm run scripts only (not npm install)
      "Bash(python -m pytest:*)",// pytest only
      "Bash(cat:*)",             // cat command (read-only)
      "Bash(echo:*)",            // echo (safe)
      "Bash(ls:*)",              // ls (read-only)
      "Bash(grep:*)",            // grep (read-only)
      "Bash(find:*)"             // find (read-only)
    ],
    "deny": [
      "Bash(rm:*)",              // Block all rm commands
      "Bash(sudo:*)",            // Block sudo
      "Bash(curl:*)",            // Block outbound HTTP
      "Bash(wget:*)",            // Block outbound HTTP
      "Bash(ssh:*)",             // Block remote access
      "Bash(chmod:*)",           // Block permission changes
      "Bash(chown:*)"            // Block ownership changes
    ]
  }
}
```

**Pattern matching rules:**
- `Bash(git:*)` — matches any `git` command regardless of subcommand or flags
- `Bash(npm run:*)` — matches `npm run <anything>` but NOT `npm install`
- `Bash(cat:*)` — matches `cat` with any arguments
- Patterns are prefix-based: `Bash(git:*)` also matches `git commit`, `git push --force`, etc.

**Enterprise gotcha:** `Bash(git push --force:*)` in allow list would permit force pushes specifically. Be careful with allow patterns that are too broad.

## Sandbox Architecture — macOS Seatbelt and Linux bubblewrap

When Claude Code runs in sandbox mode (the default for `--permission-mode default`), tool calls are executed inside a restricted sandbox environment.

### macOS: Seatbelt (App Sandbox)

macOS Seatbelt uses TrustedBSD mandatory access control. Claude Code generates a Seatbelt policy profile at runtime that permits only what is needed for the current session:

```scheme
; Seatbelt policy fragment (conceptual — actual policy is generated at runtime)
(version 1)
(deny default)

; Allow reading the project directory
(allow file-read-data
  (subpath "/path/to/your/project"))

; Allow writing only to specific paths
(allow file-write-data
  (subpath "/path/to/your/project")
  (subpath "/tmp/claude-code-sandbox"))

; Allow network access for API calls
(allow network-outbound
  (remote tcp "*:443"))

; Allow spawning child processes (for Bash tool)
(allow process-fork)
(allow process-exec)
```

**Key Seatbelt behaviors:**
- The policy is generated dynamically based on the project directory
- Attempts to write outside the allowed paths return `EPERM` immediately
- The policy is enforced at the kernel level — Claude Code's user-space code cannot bypass it

### Linux: bubblewrap (bwrap)

On Linux, Claude Code uses `bwrap` (bubblewrap) from the `bubblewrap` package. The command line used by Claude Code:

```bash
# Conceptual bwrap invocation (actual flags generated at runtime)
bwrap \
  --ro-bind /usr /usr \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --bind /path/to/project /path/to/project \
  --bind /tmp/claude-code-sandbox /tmp \
  --dev /dev \
  --proc /proc \
  --unshare-pid \
  --unshare-net \           # Network isolated from host
  -- /path/to/tool "$@"
```

**Note:** `--unshare-net` is NOT set when the Bash tool needs network access (for `curl`, `wget`, etc.). Whether network is sandboxed depends on the operation. The Bash tool inherits network access from the sandbox policy.

### Checking If Sandbox Is Active

```bash
# Inside a Claude Code session
claude --permission-mode default  # sandbox enabled

# Verify sandbox status
/status
# Shows: "Sandbox: active (bwrap)" or "Sandbox: active (Seatbelt)"
```

### `disableBypassPermissionsMode` Managed Setting

Enterprise admins can prevent users from bypassing the permission sandbox entirely:

```json
// /etc/claude-code/settings.json (Linux) or managed plist (macOS)
{
  "disableBypassPermissionsMode": true
}
```

When this is set:
- `claude --permission-mode bypassPermissions` is silently ignored and treated as `default`
- The bypass permission mode is never available, even for developers with admin rights on their own machine
- The setting is enforced at the Claude Code binary level, not just the settings layer

This is the recommended setting for enterprise deployments where security policy must be consistent across all developer machines.
