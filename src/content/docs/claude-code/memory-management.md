# Memory Management — Complete Reference

> **Version**: Claude Code v2.1.126 | **Last Updated**: May 9, 2026

---

## 1. The Memory System Overview

Claude Code's LLM backend is stateless. Every call to the Anthropic API is a fresh request — the model retains nothing between API calls except what you include in the conversation window. There is no "long-term memory" baked into the model itself.

What Claude Code provides instead is a **structured injection system**: a hierarchy of markdown files that are read from disk and inserted into the context window at specific points during a session. These files are your memory. When people say "Claude remembers my coding style," they mean a markdown file loaded into context tells Claude your coding style. When the context window fills and you run `/compact`, Claude appears to "forget" things — because those things were in conversation history, not in a persistent memory file.

**The core mental model:**

```
Memory files = Context injection at different scopes
                 (not LLM weights, not vector databases, not embeddings)
```

Every turn in your session, Claude processes:

1. The system prompt (managed internally by Claude Code)
2. All loaded memory files (injected as part of the system context)
3. The conversation history (grows every turn)
4. Tool results from previous turns

Memory files live in the "system context" portion — they are re-read and re-injected at the beginning of each turn. This is why memory files cost tokens **every single turn**, not just once.

## 2. Why Memory Architecture Matters

Understanding the memory system is not academic — it has direct, measurable impacts on your workflow, team costs, and Claude's behavior.

### Token Cost: Permanent vs. Conditional Overhead

Every byte in a CLAUDE.md file costs input tokens on **every single API call** during a session. A 5,000-token CLAUDE.md file that runs 50 turns costs 250,000 tokens in overhead alone, before any actual work happens.

This is different from conversation history, which also grows — memory files are a **fixed, permanent per-turn overhead**. Conversation history is variable (grows with the session, compacted away with `/compact`).

| Memory File | Cost Model | Survives /compact? | When to Optimize |
|---|---|---|---|
| Enterprise CLAUDE.md | Fixed, per-turn | Yes (re-read) | When IT team deploys verbosely |
| User CLAUDE.md | Fixed, per-turn | No (not re-read) | When it grows beyond 2KB |
| Project CLAUDE.md | Fixed, per-turn | Yes (re-read) | When it exceeds 4KB |
| CLAUDE.local.md | Fixed, per-turn | No | When duplicating project info |
| MEMORY.md | Fixed, capped at 200 lines | Partial (re-injected) | Rarely — cap protects you |
| Subtree CLAUDE.md | Conditional (when accessed) | No | Usually fine as-is |

### Session Continuity

Without auto-memory, every new session starts cold. Claude doesn't know that you use `pnpm`, that the project uses a monorepo structure, or that you prefer explanations before code. The memory hierarchy solves this by loading your preferences, project conventions, and accumulated knowledge at session start.

### Team Collaboration

Project CLAUDE.md is the collaboration primitive. When you commit it to git, every developer on your team gets the same project context. When you add a new API convention or a build quirk to CLAUDE.md, every teammate benefits immediately on their next Claude Code session.

### Compaction Survival

After a long session, you may run `/compact` to compress conversation history. What survives? Only what's in persistent memory files. If you told Claude something mid-conversation ("use the v2 API, not v1") and didn't ask Claude to save it to MEMORY.md or add it to CLAUDE.md, it's gone after compaction.

## 3. Memory Type 1: Enterprise CLAUDE.md

### Purpose

Enterprise CLAUDE.md is the IT administrator's tool for enforcing organization-wide behavior across all Claude Code users on managed machines. It is the highest-priority memory file, loaded first, and cannot be excluded, overridden, or blocked by users.

### File Locations

```
macOS:   /Library/Application Support/ClaudeCode/CLAUDE.md
Linux:   /etc/claude-code/CLAUDE.md
Windows: %PROGRAMDATA%\ClaudeCode\CLAUDE.md
         (typically C:\ProgramData\ClaudeCode\CLAUDE.md)
```

### Deployment Methods

Enterprise CLAUDE.md is typically deployed through system management tooling:

**macOS (Jamf Pro):**
```xml
<!-- Script payload in Jamf policy -->
<script>
#!/bin/bash
mkdir -p "/Library/Application Support/ClaudeCode"
cat > "/Library/Application Support/ClaudeCode/CLAUDE.md" << 'POLICY_EOF'
# Acme Corp — Claude Code Policy

## Security Requirements
- Never output secrets, credentials, or API keys
- Do not access files outside the project directory without explicit user approval
- All generated code must follow OWASP secure coding guidelines

## Compliance Standards
- PCI-DSS: Do not generate, process, or log cardholder data
- SOX: All financial calculation logic must include audit comments

## Code Standards
- All production code must include error handling
- Use the internal Acme logging library (acme-logger v3) for all logging
POLICY_EOF
chmod 644 "/Library/Application Support/ClaudeCode/CLAUDE.md"
</script>
```

**Linux (Ansible):**
```yaml
# ansible/roles/claude-code/tasks/main.yml
- name: Create Claude Code config directory
  file:
    path: /etc/claude-code
    state: directory
    mode: '0755'
    owner: root
    group: root

- name: Deploy enterprise CLAUDE.md
  template:
    src: templates/enterprise-claude.md.j2
    dest: /etc/claude-code/CLAUDE.md
    mode: '0644'
    owner: root
    group: root
  notify: Reload Claude Code config
```

**Windows (Group Policy / Intune):**
```powershell
# PowerShell script deployed via Intune
$claudeDir = "$env:PROGRAMDATA\ClaudeCode"
New-Item -ItemType Directory -Force -Path $claudeDir | Out-Null

$policy = @"
# Enterprise Policy — Claude Code

## Data Classification
- RESTRICTED data must never appear in prompts or outputs
- Use placeholder values when demonstrating with sensitive schemas

## Development Standards
- All commits must reference a JIRA ticket (format: ABC-1234)
- Security scanning required before merging to main

## Approved Tools
- Only use approved npm/PyPI packages from the internal registry
"@

Set-Content -Path "$claudeDir\CLAUDE.md" -Value $policy -Encoding UTF8
```

**MDM Profile (macOS/iOS/iPadOS):**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "...">
<plist version="1.0">
<dict>
  <key>PayloadContent</key>
  <array>
    <dict>
      <key>PayloadType</key>
      <string>com.apple.ManagedClient.preferences</string>
      <!-- File deployment via MDM custom profile -->
    </dict>
  </array>
</dict>
</plist>
```

### HTML Comment Stripping

All CLAUDE.md files (at every level) strip block-level HTML comments before injection into the context window. Comments inside code blocks are preserved.

```markdown
<!-- LAST REVIEWED: 2026-03-15 by security team — do not modify without approval -->
<!-- Owner: infosec@acme.com | Ticket: SEC-4421 -->

# Acme Corp Enterprise Policy

Never access internal APIs with user credentials in automated scripts.

<!-- TODO: Add section on AI governance framework once policy is finalized -->
<!-- This file is deployed via Ansible. Do not edit manually on hosts. -->
```

In the above example, all four HTML comments are stripped before Claude sees the file. Claude reads only the heading and the single instruction. This is powerful: you can annotate your enterprise policy with authorship, review dates, ticketing references, and rationale — without spending any tokens on that metadata.

### Enterprise CLAUDE.md vs. managed-settings.json

Enterprise CLAUDE.md is for **behavioral instructions** (what Claude should do or avoid). `managed-settings.json` is for **configuration enforcement** (which settings are locked, which models are permitted, which tools are allowed).

| Concern | Enterprise CLAUDE.md | managed-settings.json |
|---|---|---|
| Coding style mandates | Yes | No |
| Security behavior rules | Yes | No |
| Compliance requirements | Yes | No |
| Locking the model to claude-haiku | No | Yes |
| Disabling shell tool company-wide | No | Yes |
| Setting max token budget | No | Yes |
| Approving MCP server list | No | Yes |

Do not put instructions in `managed-settings.json` (it's JSON, not markdown). Do not put configuration values in enterprise CLAUDE.md (Claude can't enforce `maxTokens` by reading it).

### What Cannot Override Enterprise CLAUDE.md

- User CLAUDE.md cannot contradict it
- Project CLAUDE.md cannot contradict it
- `claudeMdExcludes` cannot exclude it
- Users cannot delete or modify the file (managed by IT)
- If a user's CLAUDE.md says "always include X" and enterprise says "never include X," enterprise wins

## 4. Memory Type 2: User CLAUDE.md (~/.claude/CLAUDE.md)

### Purpose

User CLAUDE.md stores your personal preferences and habits that apply across every project you work on. It is loaded after enterprise CLAUDE.md and before project CLAUDE.md.

### File Location

```
~/.claude/CLAUDE.md
```

This is a single file. For additional directories, see `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` below.

### HTML Comment Stripping

Same as enterprise CLAUDE.md — block-level HTML comments are stripped. Use them for personal notes:

```markdown
<!-- Updated: 2026-01-20 — added Go conventions after starting the platform-eng rotation -->
<!-- Personal preferences — do not commit this to any repo -->

# My Claude Code Preferences

## Communication Style
- Always explain the WHY before showing code
- Use analogies when introducing unfamiliar concepts
- Short code blocks with explanatory comments are better than large undocumented blocks

## My Background
- Primary languages: Go, Python, some TypeScript
- Comfortable with: Kubernetes, Terraform, PostgreSQL
- Learning: Rust, distributed tracing systems
```

### Good Content for User CLAUDE.md

These are preferences that apply universally, regardless of project:

```markdown
# My Personal Preferences

## Code Style (Language-Specific)
- Go: Use `errors.As` not `errors.Is` for type assertions; use `slog` for logging
- Python: Black formatting; type hints on all function signatures; ruff for linting
- Shell: Prefer `#!/usr/bin/env bash` and `set -euo pipefail`
- SQL: uppercase keywords, snake_case identifiers, explicit column lists (no SELECT *)

## Response Format
- Provide tests alongside any new function you write, without being asked
- When refactoring, show me the before/after diff in a code block
- Prefer explaining trade-offs over picking "the best" answer

## Interaction Habits
- I prefer short, dense answers unless I ask for explanation
- Call out any assumption you're making that could be wrong
- When you're uncertain, say so explicitly rather than guessing

## Cross-Project Shortcuts
- "the DB" usually means the primary PostgreSQL instance in whatever project I'm in
- "the infra repo" means ~/code/acme-infrastructure
- "our style guide" means https://style.acme.internal/engineering
```

### Bad Content for User CLAUDE.md

These belong in project CLAUDE.md instead:

```markdown
# DON'T PUT THIS IN USER CLAUDE.md:

## Project: Widget Service  ← This is project-specific
- Use the WidgetRepository abstraction, not direct DB calls
- The legacy `widget_v1` table must not be written to

## Build Commands  ← Project-specific
- Always use `./scripts/build.sh`, never `go build` directly
```

Anything project-specific in user CLAUDE.md means Claude gets confused context when working on other projects. If you're in a Python project and your user CLAUDE.md talks about Go conventions, those Go conventions still consume tokens.

### CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD

You can configure additional directories whose CLAUDE.md files are loaded as if they were user CLAUDE.md files:

```bash
# In ~/.bashrc, ~/.zshrc, or ~/.claude/settings.json env section
export CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD="/shared/team-policies:/company/standards"
```

This is useful for:
- Shared team policy directories mounted on developer machines
- Consulting situations where you have a "client policy" CLAUDE.md separate from personal preferences
- Splitting user memory into thematic files (`~/claude-styles/CLAUDE.md`, `~/claude-security/CLAUDE.md`)

The directories in this list are searched for CLAUDE.md files and loaded in the order listed, after user CLAUDE.md, before project CLAUDE.md.

### Excluding User CLAUDE.md

If you need to exclude your user CLAUDE.md for a specific project (perhaps it conflicts with strict enterprise policy, or you're working in a context where personal preferences shouldn't bleed in):

```json
// .claude/settings.json (project-level)
{
  "claudeMdExcludes": ["~/.claude/CLAUDE.md"]
}
```

## 5. Memory Type 3: Project CLAUDE.md

### Purpose

Project CLAUDE.md is the most important memory file for day-to-day team development. It is committed to git, shared with all team members, and contains team-agreed conventions, project architecture, build commands, and institutional knowledge.

### File Locations (in search order)

Claude Code checks both locations. If both exist, both are loaded (project root takes precedence in conflict):

```
./CLAUDE.md                  (project root — preferred location)
./.claude/CLAUDE.md          (alternative — keeps root clean)
```

### Auto-Generation with /init

For new projects, run `/init` to have Claude scan the project and generate an initial CLAUDE.md:

```
> /init

Analyzing project structure...
  Found: package.json (Node.js, pnpm workspace)
  Found: prisma/schema.prisma (PostgreSQL via Prisma)
  Found: src/ with React TypeScript components
  Found: Dockerfile and docker-compose.yml
  Found: .github/workflows/ (CI/CD)

Generating CLAUDE.md...
✓ Created CLAUDE.md (342 lines)

Review and commit to git to share with your team.
```

The generated file covers detected build systems, test runners, database migration commands, and common conventions observed in the codebase.

### HTML Comment Stripping

```markdown
<!--
  CLAUDE.md for Widget Platform Monorepo
  Team: Platform Engineering
  Last major update: 2026-02-14 (added gRPC conventions)
  Reviewers: @alice, @bob, @carol
  
  This file is the team's shared memory. Before making changes:
  1. Discuss in #platform-eng Slack channel
  2. Create PR for review
  3. Update the "Last major update" line above
-->

# Widget Platform — Development Guide

...
```

None of the comment block above reaches Claude. The file serves double duty: rich annotation for humans, clean instructions for Claude.

### @import Syntax

Large projects often need modular CLAUDE.md organization. Use `@` imports to split your memory across files:

```markdown
<!-- Main CLAUDE.md — loads shared domain files -->

# Widget Platform

## Core Architecture
@.claude/architecture.md
@.claude/api-conventions.md
@.claude/database-patterns.md

## Service-Specific
@services/auth/CLAUDE.md
@services/billing/CLAUDE.md
@services/notifications/CLAUDE.md

## Infrastructure
@infra/kubernetes/CLAUDE.md
```

Each imported file can contain its own imports (up to 5 recursive levels). Files imported with `@` are loaded at the same time as the parent — they are not lazy.

### Survival of /compact

This is the critical distinction: **project CLAUDE.md is re-read from disk** when `/compact` runs. After compaction, conversation history is summarized, but Claude Code re-loads all CLAUDE.md files from disk before generating the summary. This means:

- Project conventions persist through compaction
- Architecture decisions documented in CLAUDE.md persist
- Team shortcuts and commands persist

But **user CLAUDE.md is NOT re-read after compaction** (it was already loaded into the pre-compaction context that got summarized). This asymmetry is why critical project information should live in project CLAUDE.md, not user CLAUDE.md.

### Best Content Patterns by Tech Stack

**Node.js / TypeScript Project:**
```markdown
# Acme Widget Service

## Project Overview
REST API + React frontend. PostgreSQL via Prisma. Redis for caching.
Monorepo managed with pnpm workspaces.

## Commands
- Install: `pnpm install` (never npm or yarn)
- Dev: `pnpm dev` (starts API on :3001, web on :3000)
- Test: `pnpm test` (vitest, ~12s full suite)
- Build: `pnpm build` (outputs to dist/)
- DB migrate: `pnpm prisma migrate dev`
- DB reset: `pnpm prisma migrate reset --force`
- Type check: `pnpm tsc --noEmit`

## Code Conventions
- All API handlers in `src/api/handlers/` — never inline in router files
- Business logic in `src/domain/` — handlers call domain, domain is pure
- Database access only through repositories in `src/repositories/`
- Never call `prisma.` directly outside of repository files
- Use `zod` for all input validation — never trust unvalidated data

## Testing
- Unit tests: co-located as `*.test.ts`
- Integration tests: `tests/integration/` — require running Docker stack
- E2E tests: `tests/e2e/` — require full deployed environment
- Run integration tests with: `docker-compose up -d && pnpm test:integration`

## Known Issues / Gotchas
- The `payment-service` dependency has a bug with amounts > $10,000 (ticket WGT-2341)
- Redis connection pool limit is 20; don't create new connections in hot paths
- `pnpm prisma generate` must be run after any schema change before TypeScript compiles
```

**Python / Django Project:**
```markdown
# Data Platform API

## Setup
- Python 3.12 via pyenv (`.python-version` file sets it automatically)
- Virtual env: `python -m venv .venv && source .venv/bin/activate`
- Install: `pip install -e ".[dev]"`
- Never use global pip install

## Commands
- Dev server: `python manage.py runserver`
- Tests: `pytest` (not `python -m pytest`, not `python manage.py test`)
- Coverage: `pytest --cov=src --cov-report=html`
- Migrations: `python manage.py makemigrations && python manage.py migrate`
- Linting: `ruff check . && mypy src/`
- Format: `ruff format .`

## Architecture
- Django for ORM + admin; DRF for API
- Celery for async tasks — Redis as broker
- All task definitions in `src/tasks/` — never inline
- Custom managers in `src/models/managers.py`
- All serializers in dedicated `serializers.py` per app, not in views.py
```

**Go Project:**
```markdown
# Platform Service (Go)

## Build
- `make build` — builds to `./bin/`
- `make test` — runs all tests with race detector
- `make lint` — golangci-lint with project config
- `make generate` — runs all `//go:generate` directives
- Never use `go run` in production — always `make build`

## Conventions
- Errors: wrap with `fmt.Errorf("context: %w", err)` — never discard
- Logging: `slog` only — no `log.Printf`, no `fmt.Println` in library code
- Context: always first argument, always named `ctx`
- Tests: table-driven, subtests via `t.Run()`, `testify` for assertions
- No global state — pass dependencies via constructor injection

## Internal Packages
- `internal/db` — all database access (PostgreSQL via pgx)
- `internal/cache` — Redis client wrapper
- `internal/api` — HTTP handlers (chi router)
- `pkg/` — code safe for external import (keep minimal)
```

## 6. Memory Type 4: CLAUDE.local.md

### Purpose

CLAUDE.local.md is your personal, machine-local override file for a specific project. It's automatically added to `.gitignore` by Claude Code — teammates never see it, and it's not committed to the repository.

### File Locations

```
./CLAUDE.local.md                (project root)
./.claude/CLAUDE.local.md        (alternative location)
```

### What to Put Here

Personal developer preferences that apply to this project but shouldn't become team policy:

```markdown
# My Local Overrides — Widget Service

## My Dev Environment
- My local DB is on port 5433 (not 5432) — docker-compose uses host mapping
- I run the auth service separately on :8080 — skip the auth mock in tests
- Use `make dev-local` instead of `make dev` (uses my local config)

## Personal Shortcuts
- "the admin panel" means http://localhost:3000/admin in my setup
- I've aliased `wt` to `pnpm test --watch` in my shell

## Active Work
- Currently working on the billing refactor (WGT-1892)
- Ignore the legacy payment adapter — I'm replacing it, don't refactor it

## Debug Flags
- Add `DEBUG_BILLING=1` to env when testing billing flows
- My Stripe webhook secret is in ~/.secrets/stripe-local.env (never commit)
```

### Worktree Caveat

CLAUDE.local.md does **not** cross git worktree boundaries. Each worktree has its own working directory, so `./CLAUDE.local.md` in worktree A is not the same file as `./CLAUDE.local.md` in worktree B.

If you want personal preferences that apply across all worktrees of a repository, use either:

1. User CLAUDE.md (`~/.claude/CLAUDE.md`) for truly personal preferences
2. `@~/.claude/myproject-overrides.md` imported from your user CLAUDE.md
3. A file in a directory covered by `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`

### Comparison: Team vs Personal vs Local

```

│ DECISION MATRIX: Where Does This Info Belong?                    │

│                                                                  │

│                                                                  │
│  "My local DB is on a non-standard port"                         │

│                                                                  │
│  "Company mandates OWASP secure coding"                          │
│  → Enterprise CLAUDE.md ✓ (IT deploys, all users)               │
│                                                                  │
│  "Remember that I'm working on the auth refactor this week"      │
│  → CLAUDE.local.md or MEMORY.md ✓ (temporal project context)    │
```

## 7. Memory Type 5: Auto-Memory MEMORY.md

### Purpose

Auto-Memory is Claude Code's per-project, machine-local memory system that Claude manages autonomously. Unlike CLAUDE.md files (which you write), MEMORY.md is maintained by Claude itself — when you say "remember that we use pnpm" or "note that the auth service is down this week," Claude updates the MEMORY.md file.

### File Location

```
~/.claude/projects/<project-hash>/memory/MEMORY.md
```

The `<project-hash>` is a deterministic hash of the project root path. All git worktrees of the same repository share a single memory directory (since they share the same git root).

To find your project's memory directory:

```bash
# The hash is based on the canonical project path
# You can inspect it directly:
ls ~/.claude/projects/

# Or ask Claude:
> /memory show path
~/.claude/projects/a3f9b2c1d4e5/memory/MEMORY.md
```

### Size Limits and the 200-Line Window

MEMORY.md has a **hard cap of 200 lines or 25KB, whichever is smaller**, applied at session start. If your MEMORY.md grows beyond this limit, only the first 200 lines are loaded into context. This cap protects you from runaway memory growth — it guarantees memory overhead stays bounded.

The 200-line window means you should put the most important information near the top of MEMORY.md. Claude Code, when managing this file automatically, attempts to keep higher-priority items at the top.

### Satellite Topic Files

For organized memory across topics, MEMORY.md can reference satellite files:

```markdown

- Run tests before proposing any PR
- Prefer small focused commits over large ones

## See Also
<!-- Satellite memory files for organized topics -->
@./tech-decisions.md
@./current-sprint.md
@./known-issues.md
```

Satellite files live in the same `~/.claude/projects/<hash>/memory/` directory.

### Purpose

When you use Claude Code in multi-agent or subagent mode, individual subagents can maintain their own persistent memory. ### Three Memory Scopes


## 9. Subtree CLAUDE.md — On-Demand Directory Memory

### Purpose

You can place a `CLAUDE.md` file in any subdirectory of your project. These "subtree" CLAUDE.md files are loaded **lazily** — only when Claude reads, edits, or otherwise touches files within that directory during a session.

This is different from all other CLAUDE.md types, which are loaded eagerly at session start.

### Load Trigger

When Claude accesses a file at `src/billing/invoice.ts`, Claude Code checks for:

```
src/billing/CLAUDE.md
src/CLAUDE.md           (if not already loaded)
CLAUDE.md               (already loaded at session start)
```

It loads any subtree CLAUDE.md files it finds along the path that haven't been loaded yet. The `InstructionsLoaded` hook fires for each new load (see below).

### Example: Monorepo Subtree Structure

```
my-monorepo/
├── CLAUDE.md                    ← Loaded at session start (global conventions)
├── packages/
│   ├── api/
│   │   ├── CLAUDE.md            ← Loaded when Claude touches packages/api/**
│   │   └── src/
│   ├── web/
│   │   ├── CLAUDE.md            ← Loaded when Claude touches packages/web/**
│   │   └── src/
│   └── shared/
│       ├── CLAUDE.md            ← Loaded when Claude touches packages/shared/**
│       └── src/
├── services/
│   ├── auth-service/
│   │   └── CLAUDE.md            ← Domain-specific rules for auth
│   └── payment-service/
│       └── CLAUDE.md            ← Domain-specific rules for payments
└── infra/
    └── CLAUDE.md                ← IaC-specific rules
```

**packages/api/CLAUDE.md example:**
```markdown
# API Package — Claude Instructions

This package is the Express.js REST API backend.

## Conventions
- Route handlers in `src/routes/` — never business logic in routes
- Middleware in `src/middleware/`
- All DB access via `src/repositories/` only

## Testing
- Run: `pnpm test --filter=@widget/api`
- Test DB: automatically managed by vitest setup
- Mock external services: use `src/__mocks__/` directory

## Current Status (2026-04-15)
- Migrating from Express 4 to Express 5 — do not use v4-only APIs
- The auth middleware is being rewritten — don't modify `src/middleware/auth-legacy.ts`
```

### InstructionsLoaded Hook

You can hook into subtree CLAUDE.md loading for logging or triggering side effects:

```json
// .claude/settings.json
{
  "hooks": {
    "InstructionsLoaded": [
      {
        "matcher": { "path": "src/payments/**" },
        "command": "echo 'Payment domain loaded — PCI-DSS rules active' >> /tmp/claude-audit.log"
      }
    ]
  }
}
```

### Compaction Behavior

Subtree CLAUDE.md files do **not** automatically survive `/compact`. When you run `/compact`:

1. Project root CLAUDE.md is re-read from disk ✓
2. Subtree CLAUDE.md files loaded in the session are NOT re-loaded ✗

They will be re-loaded when Claude next accesses a file in their directory. For long sessions where you're working across many parts of a monorepo, this can cause "forgetting" of subtree-specific rules after compaction.

**Workaround**: Import critical subtree files from the root CLAUDE.md:

```markdown
# Root CLAUDE.md
@packages/api/CLAUDE.md
@services/auth-service/CLAUDE.md
```

This makes those files load eagerly at session start and re-load after compaction, at the cost of always loading them even when not relevant.

## 10. The @import Syntax

### Overview

Any CLAUDE.md file (at any level) can import other files using the `@` syntax:

```markdown
@relative/path/to/file.md
@/absolute/path/to/file.md
@~/path/relative/to/home.md
```

Imports are resolved at load time and the imported content is inlined into the importing file before injection into the context window.

### Resolution Rules

| Path Format | Resolution |
|---|---|
| `@file.md` | Relative to the importing CLAUDE.md's directory |
| `@./file.md` | Same as above (explicit relative) |
| `@../file.md` | Parent directory |
| `@/absolute/path.md` | Absolute filesystem path |
| `@~/documents/style.md` | Home directory expansion |

### Recursion Limit

Imports can nest up to **5 hops deep**:

```
CLAUDE.md
  @.claude/architecture.md         (hop 1)
    @.claude/api-design.md         (hop 2)
      @.claude/rest-conventions.md (hop 3)
        @.claude/http-codes.md     (hop 4)
          @.claude/errors.md       (hop 5 — maximum)
            @.claude/deeper.md     (hop 6 — NOT IMPORTED, silently ignored)
```

Circular imports are detected and broken (the second occurrence of a file is skipped).

### Code Block Preservation

The `@` import syntax is **not** processed inside code blocks:

````markdown
# Using @imports

This file imports our API conventions:
@.claude/api-conventions.md

Here's an example of the import syntax (not executed):
```
@some/path/file.md   ← This is NOT imported — it's in a code block
```
````

### Token Cost

Imported files are loaded at the same time as the parent — they are not lazy-loaded. The total token cost of a CLAUDE.md file with imports is:

```
Total tokens = tokens(CLAUDE.md) + tokens(imported-file-1) + tokens(imported-file-2) + ...
```

All of this overhead is paid **every turn** of the session.

### Advanced: Sharing Policies Across Projects

For organizations with multiple repositories that need to share coding standards:

```bash
# In a shared repository: acme-policies/
# Published as a git submodule or maintained separately

acme-policies/
├── security-standards.md
├── api-design-guide.md
├── data-handling.md
└── accessibility-requirements.md
```

In each project's CLAUDE.md:
```markdown
# Widget Service

## Team Policies (shared from acme-policies/)
@../acme-policies/security-standards.md
@../acme-policies/api-design-guide.md

## Widget-Specific Conventions
...
```

## 11. HTML Comment Stripping

### How It Works

Every CLAUDE.md file, at every level (enterprise, user, project, local, subtree), goes through HTML comment stripping before injection into the context window. Block-level HTML comments in the format `<!-- ... -->` are removed.

```
Before stripping:                    After stripping (what Claude sees):
─────────────────────────────────    ────────────────────────────────────
<!-- Last updated: 2026-03-01 -->    # Widget Service
<!-- Owner: alice@acme.com     -->
                                     Use pnpm for all package management.
# Widget Service

Use pnpm for all package management.
```

### What IS Stripped

Multi-line block comments:
```markdown
<!--
  This entire block is stripped.
  You can write anything here — dates, owners, rationale,
  TODO items, revision history — and Claude never sees it.
  
  Updated: 2026-01-15 by @alice
  Reviewed: 2026-01-20 by @bob, @carol
  Approved: Security team sign-off 2026-01-22
-->
```

Inline block comments (treated as block-level when on their own line):
```markdown
<!-- Section added for PCI-DSS compliance requirement 6.2.4 -->
Never log credit card numbers, even truncated.
```

### What is NOT Stripped

Comments **inside code blocks** are preserved (they are code examples, not document annotations):

````markdown
Here's how NOT to log sensitive data:

```javascript
// BAD: This logs the full credit card number
<!-- AUDIT FAIL: This pattern found in payments.js line 42 -->
console.log(`Processing card: ${cardNumber}`);
```
````

The HTML comment in the code block above is preserved and shown to Claude — it's part of the code example.

HTML attributes and inline HTML elements (not comment syntax):
```markdown
<img src="diagram.png" alt="Architecture diagram">   ← NOT stripped
<details><summary>Click to expand</summary>...</details>   ← NOT stripped
<!-- This IS stripped -->
```

### Use Cases for HTML Comments

1. **Authorship and ownership** — Who manages this file, who to contact for changes
2. **Review and approval history** — When it was reviewed, by whom, any audit trail
3. **Rationale** — Why a rule exists (regulatory requirement, past incident, etc.)
4. **TODO and maintenance notes** — Planned updates, missing sections, known gaps
5. **Version tracking** — When a rule was added, in response to which version of Claude Code
6. **Change history** — Without maintaining a separate changelog file

```markdown
<!--
  SECURITY POLICY — Enterprise CLAUDE.md
  
  Owner: Information Security Team (infosec@acme.com)
  Last reviewed: 2026-03-15 (annual review, SOC2 preparation)
  Next review due: 2027-03-15
  Approval: CISO sign-off on 2026-03-20 (ticket: SEC-7821)
  
  Change log:
  - 2026-03-15: Added AI-generated code review requirement (per NIST AI RMF)
  - 2025-11-01: Added cloud credential restriction (post-incident INC-2244)
  - 2025-04-15: Initial version
-->

# Acme Corp — Information Security Policy for Claude Code
```

## 12. Compaction Behavior

### What /compact Does

When you run `/compact` (or when automatic compaction triggers near the context limit), Claude Code:

1. Generates a summary of the current conversation
2. Discards the conversation history (tool calls, messages, results)
3. Re-reads persistent memory files from disk
4. Starts a new conversation with: [new system context + re-read memory files + summary]

### What Survives Compaction

| Memory File | Survives? | How |
|---|---|---|
| Enterprise CLAUDE.md | Yes | Re-read from disk after compaction |
| User CLAUDE.md | No | Was in pre-compaction context, gets summarized |
| Project CLAUDE.md | Yes | Re-read from disk after compaction |
| CLAUDE.local.md | No | Was in pre-compaction context, gets summarized |
| Auto-Memory MEMORY.md | Partial | Re-injected fresh from disk (200-line window) |
| Subagent MEMORY.md | N/A | Subagents have independent sessions |
| Subtree CLAUDE.md | No | Not re-loaded automatically |

The key insight: **only files with a fixed disk location that Claude Code knows to re-read will survive compaction**. The project root CLAUDE.md (and enterprise CLAUDE.md) are always re-read. Everything else was in the context window that got compacted.

### Implications

**User CLAUDE.md does not survive compaction.** If you've been working for 4 hours, ran `/compact`, and notice Claude no longer follows your personal style preferences — that's why. You need to start a new session for user CLAUDE.md to be re-loaded, or add critical personal preferences to project CLAUDE.md.

**Subtree CLAUDE.md files don't automatically survive.** After compaction, Claude no longer has the domain-specific rules from `src/payments/CLAUDE.md` loaded. They'll be re-loaded the next time Claude touches a file in that directory.

**MEMORY.md is partially preserved.** Auto-memory is re-injected after compaction, but only the first 200 lines. If you've been filling MEMORY.md with session observations, the most important items (near the top) persist; older items near the bottom may be cut off.

### Targeted /compact Instructions

Before running `/compact` in a long session, you can guide what gets preserved:

```
> /compact Focus the summary on: (1) the API design decisions we made for the 
  billing module, (2) the database schema changes we agreed on, and (3) the 
  list of files we've modified. Exclude the debugging tangents.
```

This produces a more useful post-compaction context than an unguided automatic compaction.

### Proactive Memory Saving Before Compaction

For important session discoveries, save them to memory before compacting:

```
> Note the following for project memory before we compact:
  1. The payment webhook handler must be idempotent — we use the Stripe event ID 
     as the idempotency key, stored in the processed_events table
  2. We decided to use optimistic locking (version column) in the orders table
  3. The legacy createOrder() function in orders-v1.js should not be modified —
     it's used by the mobile app which hasn't been updated yet

✓ Saved 3 items to project memory. Ready to compact.

> /compact
```

## 14. claudeMdExcludes — Selective Loading

### Purpose

`claudeMdExcludes` lets you tell Claude Code to skip specific CLAUDE.md files that would normally be loaded. This is primarily useful in monorepos where dozens of subtree CLAUDE.md files exist and you want to exclude them for performance or focus.

### Format

```json
// .claude/settings.json (project-level)
{
  "claudeMdExcludes": [
    "packages/legacy-app/**",
    "vendor/**",
    "node_modules/**",
    "docs/**/*.md"
  ]
}
```

Or in user settings (`~/.claude/settings.json`):
```json
{
  "claudeMdExcludes": [
    "~/code/old-project/**"
  ]
}
```

### Pattern Syntax

Patterns use standard glob syntax:

| Pattern | Matches |
|---|---|
| `packages/legacy/**` | All CLAUDE.md files under packages/legacy/ |
| `vendor/**` | All CLAUDE.md files anywhere under vendor/ |
| `**/test/**` | CLAUDE.md files in any test/ directory |
| `docs/internal/CLAUDE.md` | Exactly this file |
| `~/.claude/CLAUDE.md` | User CLAUDE.md (home-relative) |

### What Cannot Be Excluded

```json
// This has NO effect — enterprise CLAUDE.md cannot be excluded:
{
  "claudeMdExcludes": [
    "/etc/claude-code/CLAUDE.md",
    "/Library/Application Support/ClaudeCode/CLAUDE.md"
  ]
}
```

Enterprise CLAUDE.md is loaded by the Claude Code process before reading any project settings. There is no configuration that can bypass it.

### Use Cases

**Monorepo with noisy subtree files:**
```json
{
  "claudeMdExcludes": [
    "packages/deprecated/**",
    "tools/scripts/**",
    "third-party/**"
  ]
}
```

**Excluding user CLAUDE.md for a specific client project:**
```json
// In .claude/settings.json of the client project
{
  "claudeMdExcludes": [
    "~/.claude/CLAUDE.md"
  ]
}
```

**Excluding all subtree CLAUDE.md files (load only root):**
```json
{
  "claudeMdExcludes": [
    "src/**",
    "packages/**",
    "services/**"
  ]
}
```

## 15. Token Budget for Memory Files

### Per-File Token Costs (Estimates)

The following table uses approximate token counts. Actual costs depend on content density. Use the Claude tokenizer to get exact counts for your files.

| Memory Type | Load Timing | Size Limit | Typical Size | Approx Tokens | Per-Turn Cost | Optimization |
|---|---|---|---|---|---|---|
| Enterprise CLAUDE.md | Session start | No limit (use sparingly) | 0.5–3KB | 125–750 | Always | Keep focused on must-have policy |
| User CLAUDE.md | Session start | No limit (practical ~10KB) | 1–5KB | 250–1,250 | Always | Split by domain, use @imports |
| Project CLAUDE.md | Session start | No limit (practical ~20KB) | 2–15KB | 500–3,750 | Always | Use @imports for modularity |
| CLAUDE.local.md | Session start | No limit (practical ~5KB) | 0.5–2KB | 125–500 | Always | Only local overrides |
| Auto-Memory MEMORY.md | Session start | 200 lines / 25KB | Variable | 0–1,500 | Always (capped) | Prune low-value entries |
| Subagent MEMORY.md | Agent invocation | 200 lines / 25KB | Variable | 0–1,500 | Per-agent | Same as auto-memory |
| Subtree CLAUDE.md | First file access | No limit | 0.5–5KB | 125–1,250 | When active | Keep domain-focused |
| @imported files | Same as parent | No limit | Variable | Variable | With parent | Avoid deeply nested imports |

### Total Session Overhead Calculation

For a typical well-configured team setup:

```
Enterprise CLAUDE.md:      500 tokens (2KB policy doc)
User CLAUDE.md:          1,000 tokens (4KB personal prefs)
Project CLAUDE.md:       2,000 tokens (8KB with @imports)
CLAUDE.local.md:           250 tokens (1KB local overrides)
Auto-Memory MEMORY.md:     750 tokens (100 lines of memory)
Active subtree CLAUDE.md:  500 tokens (when in a domain area)
─────────────────────────────────────────────────────────
Total overhead per turn: ~5,000 tokens

At claude-sonnet-4-6 input pricing:
  5,000 tokens × 50 turns = 250,000 tokens × $3/million = $0.75/session
```

For comparison, a single large CLAUDE.md of 20KB:
```
20KB ≈ 5,000 tokens × 50 turns = 250,000 tokens
Same cost, but less organized and harder to maintain
```

The overhead is the same whether organized or monolithic — the organizational pattern doesn't affect token cost.

### Optimization Strategy

**Reduce fixed overhead:**
1. Keep enterprise CLAUDE.md minimal (only true org-wide policy)
2. Keep user CLAUDE.md to truly universal preferences
3. Move project-specific items from user CLAUDE.md to project CLAUDE.md
4. Use HTML comments for all human-only metadata (zero token cost)
5. Remove duplicate information across memory levels

**Use conditional loading:**
1. Move domain-specific rules to subtree CLAUDE.md (only loaded when relevant)
2. Use `claudeMdExcludes` to skip unused directories in large monorepos
3. Prefer subtree CLAUDE.md over monolithic project CLAUDE.md for large teams

**Cap auto-memory growth:**
1. Periodically review and prune MEMORY.md via `/memory edit`
2. Delete observations that are no longer accurate or useful
3. The 200-line cap prevents runaway growth, but quality matters too

## 16. Patterns for Large Teams & Monorepos

### Pattern 1: Modular CLAUDE.md with @imports

For a large monorepo with many domain areas, organize with a thin root file and deep imports:

```
.claude/
├── CLAUDE.md            ← Root: imports only, plus global conventions
├── architecture.md      ← System architecture overview
├── api-conventions.md   ← REST/gRPC conventions
├── database-patterns.md ← ORM patterns, migration rules
├── testing-strategy.md  ← Test pyramid, coverage requirements
├── security-policy.md   ← Security rules (imported from infosec team's shared doc)
└── deployment-guide.md  ← How to deploy, rollback, and monitor
```

**Root CLAUDE.md:**
```markdown

  Make changes via PR with team review

# Widget Platform

- Test runner: Vitest

@.claude/api-conventions.md

@.claude/security-policy.md
```

### Pattern 2: Subtree CLAUDE.md for Bounded Contexts

In a services monorepo, each service gets domain expertise:

```
services/
├── auth-service/
│   └── CLAUDE.md      ← Auth-specific: JWT, OAuth flows, session management
├── payment-service/

└── analytics-service/
    └── CLAUDE.md      ← Analytics-specific: data warehouse schema, metrics
```

Each subtree CLAUDE.md only loads when Claude works in that service, keeping base overhead minimal.

### Pattern 3: Enterprise Policy + Team Conventions

```
/etc/claude-code/CLAUDE.md    ← IT manages: security, compliance, legal
./CLAUDE.md                    ← Team manages: coding conventions, workflows
./.claude/CLAUDE.local.md      ← Individual manages: personal overrides
```

```markdown
# ACME — Enterprise Policy
```

### Pattern 4: Per-Package CLAUDE.md in Monorepos

For pnpm/Turborepo/Nx monorepos where each package has its own team:

```
packages/
├── @acme/ui/
│   └── CLAUDE.md          ← UI library: design tokens, accessibility, Storybook
├── @acme/api-client/
│   └── CLAUDE.md          ← API client: generated types, versioning policy
├── @acme/auth/
│   └── CLAUDE.md          ← Auth package: security-sensitive, extra scrutiny
└── @acme/data/
    └── CLAUDE.md          ← Data package: schema conventions, migration rules
```

**Root CLAUDE.md — minimal and cross-cutting only:**
```markdown
# Acme Monorepo

## Workspace Commands
- Install: `pnpm install` (run from root)
- Build all: `pnpm turbo build`
- Test all: `pnpm turbo test`
- Build single package: `pnpm turbo build --filter=@acme/ui`

## Cross-Package Conventions
- Package names: `@acme/<package-name>` 
- All packages export TypeScript types
- Changelogs: automated via changesets (`pnpm changeset`)
- Never import internal packages directly — use workspace protocol: `"@acme/ui": "workspace:*"`

## Package-Specific Details
See CLAUDE.md in each package directory for package-specific conventions.
These files are loaded automatically when you work in that package.
```

### Pattern 5: Rules for Conditional Loading

Combine subtree CLAUDE.md with path-scoped rules in the root file:

```markdown
# Root CLAUDE.md

## Global Conventions
These apply everywhere in the codebase.
- Always use the project's TypeScript strict mode
- Every function needs JSDoc for public APIs

## Infrastructure Code (infra/, terraform/, k8s/)
When working in infrastructure directories:
- All Terraform resources must have explicit depends_on if order matters
- Never use `latest` tag for container images — always pin to digest
- Run `terraform plan` before proposing any apply

## Database Migrations (prisma/migrations/, db/migrations/)
When working with migration files:
- Never edit existing migration files — create new ones
- Migration names must be descriptive: `YYYYMMDD_HHMMSS_description`
- Always test rollback SQL before committing

## Test Files (*.test.ts, *.spec.ts, tests/**)
When working with test files:
- Tests must not depend on external services (mock or stub them)
- Each test file should be independently runnable
- Use `describe` blocks to group related tests
```

## 17. Memory Anti-Patterns

### Anti-Pattern 1: Volatile Information in Always-Loaded Files

```markdown
# BAD: User CLAUDE.md
## Current Focus (Updated Daily)
I'm currently working on the payment integration sprint.
Today's tasks: implement webhook handler, write tests for idempotency.
I'm using feature branch feat/WGT-1892-payment-webhooks.
```

This information changes every day. Put it in MEMORY.md (auto-memory handles temporal context) or CLAUDE.local.md. Putting volatile information in user CLAUDE.md means you're paying tokens for stale context.

**Better:**
```
> Remember that I'm currently on the payment integration sprint 
  (feat/WGT-1892-payment-webhooks)
```
Claude saves this to MEMORY.md and you can update it without editing a markdown file.

### Anti-Pattern 2: Enterprise CLAUDE.md for Project-Specific Rules

```markdown
# BAD: /etc/claude-code/CLAUDE.md (Enterprise)
## Widget Service Conventions
- The Widget Service uses PostgreSQL on port 5433
- Always use the WidgetRepository abstraction
- Widget Service CI pipeline: ./scripts/ci.sh
```

Enterprise CLAUDE.md applies to all projects on all managed machines. Putting Widget Service-specific rules here means every developer, on every project, on every machine gets Widget Service context injected — a massive waste of tokens and a source of confusion when working on other projects.

### Anti-Pattern 3: Keeping CLAUDE.md Too Long

```
# Dangerous sign: your CLAUDE.md is >10,000 tokens

Symptoms:
- Claude seems to ignore rules that are buried deep in the file
- Context window fills quickly
- Sessions are expensive even before any real work happens

Solutions:
1. Use @imports to split into domain files
2. Move project-specific info to subtree CLAUDE.md files
3. Move historical rationale to HTML comments (zero token cost)
4. Delete rules that are already obvious to Claude (don't document universal best practices)
5. Use auto-memory for ephemeral or frequently-changing context
```

### Anti-Pattern 4: Duplicating Info Across Memory Levels

```markdown
# BAD: Same info in multiple places

# ~/.claude/CLAUDE.md (User CLAUDE.md)
Always use pnpm, never npm or yarn.

# ./CLAUDE.md (Project CLAUDE.md)
Package manager: pnpm (never npm or yarn)

# ./CLAUDE.local.md (Local override)
Note: Use pnpm. NOT npm or yarn.
```

The `pnpm` preference consumes tokens three times per turn. Pick the right level:
- If it applies to all your projects: user CLAUDE.md
- If it's a team convention: project CLAUDE.md
- If it's redundant: delete it from the lower levels

### Anti-Pattern 5: Documenting Universal Best Practices

```markdown
# BAD: Documenting things Claude already knows

## Security Best Practices
- Sanitize all user input to prevent SQL injection
- Use HTTPS for all API calls
- Don't store passwords in plain text
- Always validate user permissions before sensitive operations
- Use parameterized queries
```

These are universal best practices that any competent model already knows. Documenting them wastes tokens without adding any new information. Use CLAUDE.md for:
- Project-specific conventions Claude can't infer
- Non-obvious decisions and their rationale
- Organization-specific tools, libraries, and patterns
- Commands and workflows unique to the project

### Anti-Pattern 6: Using MEMORY.md for Permanent Conventions

```markdown
# BAD: Using auto-memory for things that belong in CLAUDE.md

# ~/.claude/projects/a3f9b/memory/MEMORY.md
Always use the WidgetRepository abstraction for database access.
Never import prisma directly outside repository files.
Use zod for all API input validation.
The API always returns RFC 7807 error format.
Use pnpm for all package management.
```

If these are team conventions that every developer should follow, they belong in project CLAUDE.md (committed to git, available to all teammates, survives compaction reliably). Auto-memory is appropriate for:
- Personal session context ("currently working on WGT-1892")
- Discovered project facts ("the payment service has a 30s SLA")
- Machine-specific observations ("local DB is on port 5433")
- Temporary preferences ("for this session, verbose output please")
